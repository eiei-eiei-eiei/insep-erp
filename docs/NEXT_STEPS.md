### 4.5 ประเภทโรงงาน กลั่น vs แช่

> ✏️ **แก้จากแผนเดิม**: `factory_type` ต้องอยู่ที่ **`entity`** ไม่ใช่ tenant —
> ลูกค้ารายเดียวมี 2 โรง (กลั่น 1 + แช่ 1) ได้ · `entities.excise_id` มีอยู่แล้ว = เลขสรรพสามิตแยกต่อโรงได้ทันที

- กลั่น (ปัจจุบัน): หมัก→กลั่น→ปรุง→บรรจุ + ฟอร์ม ภส. ชุดกลั่น
- แช่ (เบียร์/ไวน์/สาโท): หมัก→บ่ม→บรรจุ **ไม่มีขั้นกลั่น** + ฟอร์ม ภส. คนละชุด
- ⚠️ **บล็อกอยู่**: ยังไม่มีเทมเพลตฟอร์มสุราแช่จากสรรพสามิต — ผู้ใช้มีแต่ฟอร์มกลั่น (ต้องไปขอมาก่อน)
- ⚠️ **ห้ามเปิดโหมดแช่ในระบบที่ผู้ใช้ใช้จริง** (เขาไม่ได้ทำแช่) — เป็น config เท่านั้น

**ลิงก์เดียวกันทุกคนได้** — ตัวกำหนดว่าเห็นข้อมูลใครคือ **บัญชีที่ล็อกอิน**:
`auth.uid()` → `profiles.tenant_id` → `my_tenant()` → RLS กรองทุกตาราง
(ต่อยอด pattern เดิมตรง ๆ: มี `my_role()` / `my_entities()` ใน `20260720000006_rls.sql` อยู่แล้ว)

| แบบ | URL | deploy | โชว์แบรนด์ลูกค้าที่หน้า login ได้ไหม |
|---|---|---|---|
| A. ลิงก์เดียว | `app.แบรนด์เรา.com` | 1 | ❌ (ยังไม่รู้ว่าใคร) |
| **B. subdomain ต่อลูกค้า** | `โรงก.แบรนด์เรา.com` | 1 (wildcard) | ✅ |
| C. โดเมนลูกค้าเอง | `erp.แบรนด์ลูกค้า.com` | 1 + ตั้งโดเมนต่อราย | ✅ |

> 🔗 **เชื่อมกับข้อ 2 (white-label ที่ยังค้าง)**: หน้า login อ่านแบรนด์จาก DB ไม่ได้เพราะ RLS บล็อกก่อน login
> → **แบบ B แก้ปัญหานี้พอดี** (รู้ tenant จาก subdomain ตั้งแต่ก่อนล็อกอิน) · ถ้าจะไป white-label เต็ม แบบ B แทบเป็นตัวบังคับ

> 🚨 **ห้ามใช้ subdomain/URL เป็นตัวตัดสินสิทธิ์เข้าถึงข้อมูล** — ใช้ได้แค่แต่งหน้า/ชี้ทาง
> ถ้าเขียนว่า "อยู่ subdomain ไหน = เห็นข้อมูล tenant นั้น" → ใครก็พิมพ์ URL คนอื่นแล้วเห็นข้อมูลได้
> **สิทธิ์ต้องมาจาก `profiles.tenant_id` + RLS เท่านั้น**

**ข้อมูลกิจการผู้ใช้เองควรอยู่ DB ไหน?** — แผนเดิมว่า tenant #0 ในระบบรวม แต่ควรพิจารณาแยก:
ลูกค้าคือคู่แข่งของผู้ใช้ → RLS พลาดทีเดียวรั่ว **สองทาง** · ทางที่ปลอดภัยกว่าคือให้กิจการผู้ใช้อยู่
**Supabase project ของตัวเอง แต่รันโค้ดชุดเดียวกัน** (env ชี้คนละ DB) — ยังได้ dogfooding เต็ม
และเป็น **กลไกเดียวกับ tier "ลูกค้าเป็นเจ้าของ DB"** ที่จะขายอยู่แล้ว = ไม่มีงานเพิ่ม

### 4.8 ⚡ กันระบบช้า — **ห้ามลืม อ่านก่อนเขียน migration/query ทุกครั้ง**

> ตรวจแล้ว: **ขนาดข้อมูลไม่ใช่ปัญหา** — export จริงของผู้ใช้ (หลายปี) รวม ~1.2 MB
> → ใน Postgres+index ≈ **~5 MB/ลูกค้า/3 ปี** (~2 MB/ลูกค้า/ปี)
> 8 GB (Pro) รองรับ **50 ลูกค้าได้ ~80 ปี** · 200 ลูกค้าได้ ~20 ปี → **อย่าเสียเวลากังวลเรื่องพื้นที่**

**ตัวที่ทำให้ช้าจริงคือพวกนี้ ไม่ใช่ขนาด:**

| ความเสี่ยง | กติกาที่ต้องทำ |
|---|---|
| 🔴 **ไม่มี index บน `tenant_id`** ← อันตรายสุด | **ทุก index ต้องขึ้นต้นด้วย `tenant_id`** (composite เช่น `(tenant_id, transaction_date)`, `(tenant_id, entity_id, batch)`) · ลืม = ทุก query สแกนข้อมูลลูกค้าทุกเจ้า และจะไม่รู้ตัวจนลูกค้าเยอะ |
| RLS policy แพง | helper ต้องเป็น `stable security definer` แบบเดิม (`my_role()`/`my_entities()` เขียนถูกแล้ว) — ประเมินครั้งเดียวต่อ query ไม่ใช่ต่อแถว · **อย่าเขียน subquery ตรง ๆ ใน policy** |
| connection เต็มตอนหลายเจ้าใช้พร้อมกัน | เปิด **connection pooler** ของ Supabase (Micro ~60 connections) |
| CPU/RAM ไม่พอ | อัปไซซ์ instance — จ่ายเงินแก้ได้ ไม่ต้องแก้โค้ด |

**เริ่มมองเมื่อไหร่:** < 20 ลูกค้า = ไม่ต้องคิด · 20–100 = ดู pooler + ตรวจ index · 100+ = ค่อยคิด partition

**แผนสำรองถ้าโตจริง (ไล่จากถูก→แพง):**
```
1. อัปไซซ์ compute            ← จ่ายเงิน แก้ทันที ไม่แตะโค้ด
2. ตรวจ/เพิ่ม index            ← 90% ของอาการช้าจบตรงนี้
3. ย้ายข้อมูลเก่าไปตารางเก็บถาวร (กฎหมายเก็บ 5-7 ปี ลบไม่ได้ แต่ย้ายออกจากตารางร้อนได้)
4. partition ตาราง transactions/log_* ด้วย tenant_id
5. ย้ายลูกค้ารายใหญ่ออกไป project ของตัวเอง   ← = tier แยก DB ที่ขายอยู่แล้ว
```
> 💡 ข้อ 5 คือ **สินค้า tier พรีเมียมกับแผนสำรองเป็นของชิ้นเดียวกัน** → ยิ่งตอกย้ำว่า provision/fleet script ต้องทำตั้งแต่แรก

### 4.9 เซ็ตอัพ tier "แยก DB" ยุ่งแค่ไหน (ไว้ตั้งราคา)

**งานเทคนิคล้วน ๆ ≈ 45 นาที (ทำมือ) / ~10 นาที (มีสคริปต์)**: สร้าง project + เชิญเราเป็น member →
`db:push` 24 migration → seed ค่าตั้งต้น → สร้าง user/role → Vercel env+โดเมน
**ตัวกินเวลาจริงคือย้ายข้อมูลเดิม (ชม.–วัน) + เทรน (2-4 ชม.) ซึ่งเท่ากันทั้งสอง tier**

⚠️ **ต้นทุนที่ซ่อนอยู่สำคัญกว่าตอนติดตั้ง**: ออก version ใหม่ที่มี migration = ต้องรัน **ทุก DB**
(มี fleet script = ไม่กี่นาที · ไม่มี = นรกตอนลูกค้า 10 ราย) + backup ต้องวน + support ต้องรู้ว่าเจ้าไหนอยู่ DB ไหน

→ **ตั้งราคา tier แยก DB บวก +฿500–990/เดือน** (หรือค่าติดตั้ง +฿5,000) เพราะแบกงานต่อ release ตลอดอายุลูกค้า
· ถ้าลูกค้าเปิด Supabase **Free ของตัวเอง** ค่า infra ที่เราแบก = ฿0 → ส่วนต่างเป็นค่าดูแลล้วน = มาร์จิ้นดี

## 7. บทเรียนจาก D43 (อ่านก่อนแก้ UI/เขียนสคริปต์)

1. **selector trap**: `data-mode` อยู่บน `<html>` แต่ `data-brand` อยู่บน div ใน `(app)/layout.tsx`
   → `[data-mode="dark"][data-brand="x"]` **ไม่ match** ต้องเขียนคู่กับแบบลูกหลาน
   **build ผ่านทั้งที่สีผิด** — จับได้ตอนอ่าน computed style ในเบราว์เซอร์เท่านั้น
2. **สคริปต์ sweep**: ห้าม `replace()` แบบ global ที่แตะ `"` — รอบแรกไปกิน string literal ทั้งไฟล์
   (`from "react"` → `from"react"`) ต้อง revert · แก้เฉพาะ "ภายในค่าของ className"
3. **หลัง sweep สีอัตโนมัติ ต้องไล่หาคู่ `bg-x` + `text-x` ที่เป็น token เดียวกัน**
   (เจอปุ่มสแกนใบเสร็จกลายเป็น `bg-brand text-brand` = ตัวหนังสือหายไปกับพื้น)
4. **ไฟล์เอกสารพิมพ์ห้ามผูกกับธีม**: `print.ts` · `reportHtml.ts` · `lib/pdf/*`
   ต้องดำบนขาวเสมอ ไม่งั้นเปิดโหมดมืดแล้วพิมพ์ = กระดาษพื้นดำ
5. **ตรวจสีดิบเหลือ 0**:
   ```bash
   grep -rn "\(bg\|text\|border\)-\(slate\|amber\|green\|red\|blue\)-[0-9]" app --include=*.tsx | grep -v print.ts
   ```
