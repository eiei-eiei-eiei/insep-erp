## 3. โลโก้ — **ผู้ใช้ไม่มีโลโก้บริษัท แต่ลูกค้าที่ซื้อโปรแกรมอาจมี**

> ผู้ใช้ยืนยัน 2026-08-02: ตัวเองไม่มีโลโก้ → **ห้ามทำให้เอกสารของผู้ใช้เปลี่ยนหน้าตา**
> แต่ต้องรองรับให้ลูกค้าที่มีโลโก้ใช้ได้ → ทำเป็น "มีก็ขึ้น ไม่มีก็เหมือนเดิมเป๊ะ"

ตอนนี้ `logo_url` ใน `app_settings` ต้อง **วาง URL เอง** ยังไม่มีปุ่มอัปโหลด
ถ้าไม่ใส่ → แถบเมนู fallback เป็นตัวอักษรแรกของ `brand_name` ในกล่องสีแบรนด์ (ดูตั้งใจ ไม่ได้ดูขาด)

**งานที่ต้องทำ (ยังไม่เริ่ม)**:
1. สร้าง bucket `branding` ใน Supabase Storage (public read)
2. ปุ่มอัปโหลดในการ์ด "แบรนด์ของกิจการ" (`BrandingCard.tsx`) — ตอนนี้วาง URL อย่างเดียว
3. **โลโก้บนหัวเอกสารการค้า** — ที่ต้องคิดเรื่องการจัดวาง:
   - หัวกระดาษปัจจุบัน (`companyHeader` ใน `print.ts`) เป็น `<table>` 2 ช่อง 50/50 —
     **ซ้าย** = ชื่อไทย/อังกฤษ + ที่อยู่ + เลขภาษี · **ขวา** = ชื่อเอกสาร + ต้นฉบับ/สำเนา
   - แผนที่เสียหายน้อยที่สุด: แทรก `<td>` โลโก้ **ซ้ายสุด** กว้าง ~90px (`img` สูงคงที่ 56px,
     `object-fit:contain`) แล้วลดช่องซ้ายเป็น ~40% — **ช่องขวาไม่ขยับ** เลขเอกสาร/ยอดเงินอยู่ที่เดิม
   - ⚠️ **ไม่มี `logo_url` = ไม่ render `<td>` นั้นเลย** (ไม่ใช่ `<td>` ว่าง) → เอกสารของผู้ใช้เหมือนเดิม 100%
   - ⚠️ ต้องเป็น **URL ที่ public read** — หน้าต่างพิมพ์เป็น `window.open` เขียน HTML ใหม่ ไม่มี session/cookie
     ของแอปติดไปด้วย · โลโก้ที่ต้อง auth จะไม่ขึ้นตอนพิมพ์
   - ⚠️ ต้อง **รอรูปโหลดเสร็จก่อน `w.print()`** — โค้ดตอนนี้รอแค่ `document.fonts.ready` (`openPrint`)
     ถ้าไม่รอ `img.decode()` ด้วย จะได้กระดาษที่โลโก้หายหรือความสูงวัดผิด (มีตรรกะ zoom ย่อให้พอดี A4 อยู่)
   - เทสด้วยกิจการทดสอบ EID99 + โลโก้สมมติ — **ห้ามใส่ logo_url ให้กิจการจริงของผู้ใช้ตอนเทส**

**ผู้ใช้เคยถาม**: ถ้าอยากได้โลโก้/wordmark ให้ Claude ออกแบบให้ได้ — ยังไม่ได้เริ่ม

## 4. งาน productization ก้อนใหญ่ (ยังไม่เริ่ม — สถาปัตยกรรมเคาะแล้ว 2026-08-11)

> ผู้ใช้ตั้งใจ **ทำทีเดียวเป็นก้อน** ไม่ทำแทรกทีละนิด · รายละเอียดเต็มใน memory `productization-plan`

### 4.1 สถาปัตยกรรมที่ตัดสินแล้ว — อย่ารื้อ อย่าเปิดประเด็นซ้ำ

| เรื่อง | มติ | เหตุผล (อย่าลืม ไม่งั้นจะถูกเสนอให้เปลี่ยนอีก) |
|---|---|---|
| ที่เก็บข้อมูล | **1 Supabase project + `tenant_id` + RLS** | ดูแลง่าย: migrate/backup/deploy ครั้งเดียว |
| ~~1 project ต่อลูกค้า~~ | ❌ **ยกเลิกมติเดิม** | เปลี่ยนเป็น multi-tenant แล้ว (แผนเก่าเขียนว่าแยก project — ไม่ใช้แล้ว) |
| ความเชื่อมั่นลูกค้า | **สัญญาลายลักษณ์อักษร (NDA/DPA) + เข้ารหัส at-rest + audit log** | พูดได้แค่ *"เปิด DB ตรง ๆ อ่านไม่ได้"* — **ห้ามพูดว่า "เราอ่านไม่ได้"** เพราะกุญแจอยู่ฝั่งเรา = โกหก |
| zero-access จริง | **tier ทางเลือก** — ลูกค้าเปิด Supabase ของตัวเอง | เจ้าที่กังวลสุดค่อยขายตัวนี้ |
| **E2EE (กุญแจฝั่งลูกค้า)** | ❌ **ตกไปแล้ว** | ต้องรื้อ 21 RPC + 34 DB function + 11 trigger + 61 RLS · ทำให้ **กติกาเหล็กพัง** (stock trigger, 1 batch 1 แถว, idempotency) · ลืมรหัส = ข้อมูลหายถาวร |
| codebase | **เดียว ไม่ fork** · กิจการผู้ใช้เอง = tenant #0 | แก้ฟอร์มภาษีครั้งเดียวใช้ได้ทุกเจ้า |
| โฮสต์ | Vercel Pro ทีมเดียว หลาย project | Hobby ห้ามใช้เชิงพาณิชย์ |
| ราคา | ผลิต ฿790 · +บัญชี ฿490 · +ขาย ฿490 · Full ฿1,490 · setup ฿12,000+ · **+กิจการที่ 2 ฿390–590** | |

### 4.2 EID — **ไม่ถอด** แต่ซ่อน + ขายเป็น add-on ที่ผู้ใช้เป็นคนเปิดให้

> ⚠️ **ห้ามลบระบบ EID** — กิจการผู้ใช้เองใช้ 2 entity จริง (EID01 บริษัท จด VAT + EID02 ศิวกร ส่วนตัว ไม่จด VAT
> · bank_accounts 7 บัญชีผูกข้ามทั้งสอง) · SME ไทยมี บริษัท+บุคคลธรรมดา เป็นเรื่องปกติ

- 2 ชั้น: `tenant_id` (แยกลูกค้า, RLS, ผู้ใช้ไม่เห็น) → `entity_id` (กิจการ/โรงงานของลูกค้ารายนั้น)
- `tenants.max_entities` default 1 → UI **ซ่อนตัวเลือกกิจการทั้งหมด** ยัด entity_id ให้อัตโนมัติ
- **บังคับที่ DB ไม่ใช่แค่ซ่อน UI**: RLS ห้ามลูกค้า insert/update ตาราง `entities` — สร้างได้เฉพาะ service role (ผู้ใช้)
  → เป็น add-on ที่ควบคุมได้จริง ลูกค้าเลี่ยงผ่าน API ไม่ได้

### 4.3 ทำให้ผลิต+ขาย แยกตาม entity (ขอบเขตใหม่ ยืนยัน 2026-08-11)

ตอนนี้ **มีแต่ฝั่งบัญชีที่รู้จัก entity** (transactions, tax_summaries, wht_certificates, bank_accounts,
edit_log, profiles, report_runs, snapshots) · ฝั่งผลิตกับขาย **ไม่มี entity_id เลย**

- เติม `entity_id` ฝั่งผลิต + ขาย + `contacts` (~12 ตาราง) → สินค้า/ลูกค้า/สต็อก/batch/เลขเอกสาร **แยกเด็ดขาดต่อกิจการ**
- **ต้องแก้ PK/unique พวกนี้** (ตอนนี้ unique ทั้งระบบ → 2 กิจการใช้ชื่อซ้ำกันไม่ได้):

  | ตาราง | ตอนนี้ | ต้องเป็น |
  |---|---|---|
  | `sale_menu` | `menu_name` unique | unique(entity_id, menu_name) |
  | `warehouse_stock` | PK `item_code` | PK(entity_id, item_code) |
  | `stock_product` | PK `product_id` | PK(entity_id, product_id) |
  | `log_distill` | `batch` unique ← **กติกาเหล็ก** | unique(entity_id, batch) + **แก้ golden test** |
  | `bank_accounts` | `account_name` unique | unique(entity_id, account_name) |

- **เลขเอกสารต่อกิจการ**: ไม่ต้องแก้ schema — `counters` PK เป็น `key` เดี่ยว ฝัง entity ในคีย์ได้เลย (`QU-EID02-260801`)
- ⚠️ **ผ่าตัด PK/unique ให้จบก่อนมีลูกค้าหลายเจ้า** — ทำทีหลังตอนมีข้อมูลจริงเจ็บกว่ามาก

### 4.4 กิจการที่ไม่จด VAT

- ✅ `entities.is_vat` **มีคอลัมน์อยู่แล้ว** ไม่ต้องเพิ่ม
- ต้องแตกตาม flag: `lib/sales/calc` ข้ามสูตรถอด VAT · ออกได้แค่ **ใบเสร็จรับเงิน/บิลเงินสด** · ไม่เข้า ภพ.30/tax_summaries
- ⚠️ **กฎหมาย**: กิจการไม่จด VAT **ออกใบกำกับภาษีไม่ได้ (ผิดกฎหมาย)** → ต้อง **บล็อกแข็งที่ DB/RPC** ไม่ใช่แค่ซ่อนปุ่ม

### 4.5 ประเภทโรงงาน กลั่น vs แช่

> ✏️ **แก้จากแผนเดิม**: `factory_type` ต้องอยู่ที่ **`entity`** ไม่ใช่ tenant —
> ลูกค้ารายเดียวมี 2 โรง (กลั่น 1 + แช่ 1) ได้ · `entities.excise_id` มีอยู่แล้ว = เลขสรรพสามิตแยกต่อโรงได้ทันที

- กลั่น (ปัจจุบัน): หมัก→กลั่น→ปรุง→บรรจุ + ฟอร์ม ภส. ชุดกลั่น
- แช่ (เบียร์/ไวน์/สาโท): หมัก→บ่ม→บรรจุ **ไม่มีขั้นกลั่น** + ฟอร์ม ภส. คนละชุด
- ⚠️ **บล็อกอยู่**: ยังไม่มีเทมเพลตฟอร์มสุราแช่จากสรรพสามิต — ผู้ใช้มีแต่ฟอร์มกลั่น (ต้องไปขอมาก่อน)
- ⚠️ **ห้ามเปิดโหมดแช่ในระบบที่ผู้ใช้ใช้จริง** (เขาไม่ได้ทำแช่) — เป็น config เท่านั้น

### 4.6 ที่เหลือ

- **Module feature flags** — `modules_enabled` ต่อ tenant (ผลิต/บัญชี/ขาย = 7 SKU) gate ที่ nav + route/server-action + จุดเชื่อมข้ามโมดูล
- **Provision script** สร้าง tenant ใหม่ + secrets registry + fleet cron (keep-alive + backup)
- **ตัด/ลดฟีเจอร์สแกนใบเสร็จ AI** — memory `receipt-scan-thai-unreliable` (อ่านสลิปไทยไม่แม่นพอ ขายแล้วลูกค้าผิดหวัง)
- ⚠️ **จุดเสี่ยงอันดับ 1 ของ multi-tenant**: RLS พลาด = ลูกค้าเห็นข้อมูลกัน → ต้องมี **เทสอัตโนมัติต่อ policy** ก่อนรับลูกค้าจริง

## 7. บทเรียนจาก D43 (อ่านก่อนแก้ UI/เขียนสคริปต์)

1. **selector trap**: `data-mode` อยู่บน `<html>` แต่ `data-brand` อยู่บน div ใน `(app)/layout.tsx`
   → `[data-mode="dark"][data-brand="x"]` **ไม่ match** ต้องเขียนคู่กับแบบลูกหลาน
   **build ผ่านทั้งที่สีผิด** — จับได้ตอนอ่าน computed style ในเบราว์เซอร์เท่านั้น
2. **สคริปต์ sweep**: ห้าม `replace()` แบบ global ที่แตะ `"` — รอบแรกไปกิน string literal ทั้งไฟล์
   (`from "react"` → `from"react"`) ต้อง revert · แก้เฉพาะ "ภายในค่าของ className"
3. **หลัง sweep สีอัตโนมัติ ต้องไล่หาคู่ `bg-x` + `text-x` ที่เป็น token เดียวกัน**
   (เจอปุ่มสแกนใบเสร็จกลายเป็น `bg-brand text-brand` = ตัวหนังสือหายไปกับพื้น)
4. **ไฟล์เอกสารพิมพ์ห้ามผูกกับธีม**: `print.ts` · `reportHtml.ts` · `lib/pdf/*`
   ต้องดำบนขาวเสมอ ไม่งั้นเปิดโหมดมืดแล้วพิมพ์ = กระดาษพื้นดำ
5. **ตรวจสีดิบเหลือ 0**:
   ```bash
   grep -rn "\(bg\|text\|border\)-\(slate\|amber\|green\|red\|blue\)-[0-9]" app --include=*.tsx | grep -v print.ts
   ```
