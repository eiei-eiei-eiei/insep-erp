## 1. ปัญหาที่จะแก้

ตอนนี้งานรับลูกค้าใหม่/เปลี่ยนแพ็กเกจ **ต้องพิมพ์คำสั่งใน terminal และรัน SQL ใน Supabase Dashboard**

งานที่ต้องทำซ้ำทุกครั้งที่มีลูกค้า:

| งาน | วันนี้ทำยังไง | เจ็บตรงไหน |
|---|---|---|

## 2. ข้อจำกัดที่ห้ามละเมิด (อ่านก่อนออกแบบ)

### 2.1 🚨 ตารางของแพลตฟอร์มต้องปิด RLS แบบ deny-all

ตารางใหม่ใน Postgres **ไม่มี RLS โดยปริยาย = ใครถือ anon key ก็อ่านได้** และ anon key เป็นค่าสาธารณะ
ที่ฝังอยู่ในหน้าเว็บลูกค้าทุกคน

→ ทุกตารางของแพลตฟอร์ม (บิล/ค่างวด/แอดมิน) ต้อง `enable row level security` **แล้วไม่สร้าง policy เลย**
= เข้าถึงได้เฉพาะ service role · ลูกค้ายิงตรงมาก็ได้ผลลัพธ์ว่าง

**ลืมข้อนี้ = ราคาที่ลูกค้าแต่ละเจ้าจ่าย รั่วให้ลูกค้าเจ้าอื่นเห็นหมด**

### 2.2 การเข้าถึงข้อมูลข้ามลูกค้าต้องอยู่ฝั่ง server เท่านั้น

แอดมินต้องอ่านข้อมูลข้ามทุก tenant = ต้องใช้ service role (ข้าม RLS)
→ ใช้ผ่าน server action / server component เท่านั้น · **ห้ามหลุดเข้า client bundle**
(กติกาเหล็กข้อ 6 ใน CLAUDE.md · มี `lib/supabase/admin.ts` ที่ `import "server-only"` อยู่แล้ว ใช้ตัวนั้น)

### 2.3 ต้องแยก deployment ออกจากแอปที่ลูกค้าใช้

**ข้อเสนอ**: อยู่ repo เดียวกัน โค้ดชุดเดียวกัน แต่ **เปิดใช้ได้เฉพาะ Vercel project ของแอดมิน**

- route group ใหม่ `app/(platform)/…`
- เปิดด้วย env `PLATFORM_ADMIN=1` — deployment ของลูกค้าไม่ตั้งค่านี้ → route ตอบ 404 ไปเลย
- ซ้อนด้วยตาราง `platform_admins` (uuid ของ auth user ที่เป็นแอดมิน) — env อย่างเดียวไม่พอ
  เพราะ deployment แอดมินก็ยังต้องกันคนอื่นที่บังเอิญมีบัญชี

**ทำไมไม่แยก repo/monorepo**: ต้องใช้ของร่วมกันเยอะ (`generateInitialPassword`, `isValidTenantSlug`,
`usernameToEmail`, `BRAND_COLORS`, `MODULES`) แยก repo = ก๊อปโค้ดสองชุดแล้ววันหนึ่งเพี้ยนกัน
· ถ้าวันหนึ่งอยากแยกจริง ค่อยทำตอนมีเหตุผลชัดกว่านี้

### 2.4 อยู่ DB ไหน

**DB แพลตฟอร์มลูกค้า** (`tnuxrufpzeyuvwdmkojv`) — ที่เดียวกับที่ลูกค้าอยู่
ไม่ใช่ DB ของกิจการเจ้าของระบบ (`vmhiwlxdyhatucioalzp`) ซึ่งเป็นแค่ลูกค้ารายหนึ่งที่บังเอิญเป็นตัวเอง

## 3. ขอบเขตแบ่งเป็นเฟส

### เฟส 1 — เลิกใช้ terminal ✅ **ทำเสร็จแล้ว (2026-08-13 · migration 0035 · D54)**

หน้าเดียว + ตารางรายชื่อลูกค้า — `/platform` (route group `app/(platform)/`):

| ฟังก์ชัน | ทำเสร็จที่ไหน |
|---|---|
| รายชื่อลูกค้า (slug · ชื่อ · โมดูล · โควตา/กิจการที่ใช้ · จำนวนผู้ใช้ · สร้างเมื่อไหร่) | ✅ `listTenants()` — กรอง `is_platform` ออก |
| รับลูกค้าใหม่ | ✅ `createTenant()` — สคริปต์เดิมถูกลดเหลือแค่เรียกตัวนี้ |
| เปิด/ปิดโมดูล | ✅ `setModulesAction` |
| เพิ่มกิจการ | ✅ `addEntityToTenant()` — **ด่านโควตาอยู่ในนั้น** |
| ขยายโควตา | ✅ `setQuotaAction` — ปุ่มแยก (D53) · ลดต่ำกว่ากิจการที่มีอยู่จริงไม่ได้ |
| **รีเซ็ตรหัสเจ้าของกิจการ** | ✅ `resetPasswordAction` — รหัสใหม่แสดงบนจอครั้งเดียว + ปุ่มก๊อป |

**ยังไม่ทำโดยตั้งใจ**: ปุ่มระงับลูกค้า (`tenants.is_active` ยังไม่บล็อกการล็อกอิน — ดู D54 ข้อ 6)

> ⚠️ **รหัสชั่วคราวต้องแสดงบนจอครั้งเดียวและก๊อปได้** — บทเรียนจาก 2026-08-12 ที่รหัสหายไปกับ terminal
> ห้ามเก็บรหัสดิบลง DB

**ผลลัพธ์ที่วัดได้**: รับลูกค้าใหม่จบได้โดยไม่ต้องเปิด terminal และไม่ต้องเขียน SQL เลย

### เฟส 2 — ตารางค่างวด ✅ **ทำเสร็จแล้ว (2026-08-17 · migration 0037 · D59)**

| ฟังก์ชัน | ทำเสร็จที่ไหน |
|---|---|
| ตารางค่างวดเรียงครบกำหนดเร็วสุดก่อน + ไฮไลต์ที่เลยกำหนด | `/platform/billing` |
| ปุ่ม "บันทึกว่าจ่ายแล้ว" (เลื่อน 1 รอบ + ลงประวัติ) | `recordPayment()` — เลื่อน**จากรอบเดิม ไม่ใช่จากวันนี้** |
| ประวัติการจ่าย + ย้อนรายการล่าสุด | `subscription_payments` · `voidLastPayment()` |
| **ระงับ/คืนสิทธิ์ลูกค้าค้างจ่าย** (เพิ่มจาก requirement เดิม) | `setTenantActive()` + หน้า `/suspended` |
| **แจ้งเตือนลูกค้าในแอป** (เพิ่มจาก requirement เดิม) | แถบ ≤3 วัน → ป๊อปอัพเมื่อเลยกำหนด · เฉพาะ role `main` |

**ต่างจากที่ร่างไว้เดิม (เหตุผลเต็มใน D59)**:
- `status` **ไม่มีค่า `past_due`** — เฟส 2 ไม่มี cron มาพลิกค่าให้ เก็บลง DB แล้วจะโกหก
  → คำนวณสดจาก `current_period_end < วันนี้`
- เพิ่ม `periods_paid` — จำเป็นเพื่อกัน **drift ของวันตัดรอบ** (31 ม.ค. → 28 ก.พ. → ต้องกลับเป็น 31 มี.ค.)
- เพิ่ม `tenants.billing_due_on` / `billing_notice` — มิเรอร์เฉพาะวันครบกำหนดให้ลูกค้าอ่านได้
  **แทนการเปิด policy ให้อ่าน `subscriptions`** ซึ่งจะทำให้ราคาต่อรายหลุด

<details><summary>ร่างเดิมของเฟส 2 (เก็บไว้ดูเหตุผล)</summary>

ตารางใหม่ `subscriptions` (RLS deny-all ตามข้อ 2.1):

```
tenant_id · plan (ชื่อแพ็กเกจ) · price (ต่อรอบ) · cycle ('monthly'|'yearly')
started_on · current_period_end · status ('active'|'past_due'|'paused'|'cancelled')
note
```

หน้าจอ: รายการเรียงตาม "ครบกำหนดเร็วสุดก่อน" · ไฮไลต์ตัวที่เลยกำหนด ·
ปุ่ม **"บันทึกว่าจ่ายแล้ว"** (เลื่อน `current_period_end` ไปอีก 1 รอบ + บันทึกประวัติการจ่าย)

**ยังไม่ต้องอัตโนมัติอะไรทั้งสิ้น** — แค่มีที่เดียวที่เปิดแล้วรู้ว่าใครค้าง ก็แก้ปัญหา
"มีทั้งรายเดือนรายปีแล้วสับสน" ได้เกือบหมดแล้ว

ตารางประวัติ `subscription_payments` (tenant_id · amount · paid_on · period_end_after · note)
— ไว้ตอบคำถาม "ลูกค้ารายนี้จ่ายมาแล้วกี่รอบ"

</details>

## 4. สิ่งที่ **ตัดสินใจแล้วว่าไม่ทำ**

| ไม่ทำ | เหตุผล |
|---|---|
| **ตัดบัตรเครดิตอัตโนมัติ / payment gateway** | SME ไทยโอนผ่านแอปธนาคารเป็นหลัก · ค่าธรรมเนียม + งานต่อระบบเยอะ แต่ลูกค้าไม่ได้อยากใช้ · ทวง → เขาโอน → กดยืนยัน จบ |
| **ระบบตั๋วซัพพอร์ต/feedback ในแอป** | ลูกค้ากลุ่มนี้จะทักไลน์อยู่ดี · ช่องทางที่ไม่มีใครใช้แย่กว่าไม่มี · ถ้าอยากได้ ทำแค่ปุ่ม "แจ้งปัญหา" ที่เปิดแชท LINE |
| **ให้ลูกค้าเปลี่ยนแพ็กเกจเอง** | เป็นการตัดสินใจเชิงพาณิชย์ ต้องผ่านคน · และ `tenants` จงใจไม่มี policy update (D53) |
