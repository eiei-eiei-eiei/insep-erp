## 1. ขอบเขต

### ทำ
ขายหน้าบาร์ (**เปิดบิลค้างได้**) + ออกบูธ · สต็อกวัตถุดิบ + สูตร + รับของ + ปรับยอด ·
พิมพ์ 80 มม. · QR PromptPay · ต้นทุน + กำไร + แดชบอร์ด · **ทะเบียนลูกค้า** ·
ลงบัญชีสรุปรายวันเข้ากิจการที่ตั้งไว้

### 🚫 จงใจไม่ทำ

| ไม่ทำ | เหตุผล |
|---|---|
| เชื่อมสต็อกอัตโนมัติจากบิลขายส่งของโรงงาน | บาร์ซื้อไซรัป/มะนาว/น้ำแข็งจากที่อื่นด้วย ⇒ **สองวิธีคิดในหน้าจอเดียว** · D79 พิสูจน์แล้วว่า forward อัตโนมัติพังเงียบได้เป็นปี |
| แยกสต็อกตามสถานที่ (บาร์/บูธ) | คนเดียวขนของไปกลับ ทำใบโอนทุกครั้งไม่ไหว → ใช้ **ป้ายช่องทางที่บิล** ตอบ "บูธงานนี้คุ้มไหม" แทน |
| ตรวจสอบการชำระ QR อัตโนมัติ | PromptPay ไม่มี callback ⇒ **ระบบไม่มีทางรู้ว่าจ่ายแล้วจริง** ห้ามทำท่าว่ารู้ |
| ใบกำกับภาษีอย่างย่อ | กิจการที่ตั้งไว้ไม่จด VAT · เอกสารชนิดนี้ **ยังไม่มีในระบบเลย** + ต้องขออนุมัติสรรพากรก่อน ⇒ งานก้อนใหม่ |
| เปิด/ปิดรอบกะ | ผู้ใช้ตัดสินว่าไม่ต้องการ |
| **ราคาต่างกันตามช่องทาง** (E) | ผู้ใช้ตัดสิน — ตั้งเมนูใหม่ง่ายกว่าและอ่านรายงานรู้เรื่องกว่า |
| **แต้มสะสม / ส่วนลดสมาชิก** | โครง `bar_customer` รองรับเติมทีหลังได้ แต่คนเดียวยืนบาร์ไม่มีเวลาบริหารโปรแกรมแต้ม |
| **ยิง LINE หาลูกค้าบาร์** | ต้อง LINE OA + ความยินยอมตาม PDPA ⇒ คนละระบบกับ `sendLineToTenant()` ที่มีอยู่ (นั่นคือกลุ่มของเจ้าของกิจการเอง) |
| **ระบบคืนเงิน (refund ledger)** | ยอดบิลลดลงคือความจริงที่บันทึก · เงินที่คืนหน้าเคาน์เตอร์เป็นเหตุการณ์จริงนอกระบบ — ทำครึ่ง ๆ จะได้ "ยอดเงินสดที่ควรมี" ที่เชื่อไม่ได้ |

## 2. กติกาเหล็กของโมดูลนี้

1. **🚨 `/bar` ห้ามอ่านและห้ามเขียนตารางฝั่งผลิต/ขายแม้แถวเดียว** — มีเทสอ่านซอร์สมาตรวจ
   *เหตุผล: ขายเป็นแก้วไม่เกี่ยวกับเอกสารสรรพสามิต — เผลอต่อท่อเมื่อไหร่ ตัวเลขบนฟอร์มราชการขยับโดยไม่มีอะไรฟ้อง*
2. **🚨 `bar_*.entity_id` ต้อง `not null` และ *ไม่มี* default** — ต่างจากทุกตารางในระบบโดยตั้งใจ
   บาร์ไม่ใช่กิจการหลัก · มี default แล้วลืมส่ง = ของไปลงกิจการโรงกลั่นเงียบ ๆ (ตระกูล D79)
   ไม่มี default = **insert ล้มเสียงดัง** ซึ่งดีกว่า
3. **ต้นทุนบนบิลต้องแช่ไว้ ห้ามคำนวณสด** — `cost_per_unit` ขยับทุกครั้งที่รับของ
   คำนวณสด = **กำไรเดือนที่แล้วขยับเองเมื่อเดือนนี้ซื้อของแพงขึ้น** (กติกา D75)
   ★ **แช่ตอน *เพิ่มรายการ* ไม่ใช่ตอนปิดบิล** — บิลค้าง 3 ชั่วโมงแล้วรับของใหม่ระหว่างนั้นได้
4. **เมนูที่ไม่มีสูตรและไม่มีต้นทุนตายตัว = ไม่ตัดสต็อก ต้นทุน 0 และต้องบอกบนจอ** ห้ามข้ามเงียบ (D83/D86)
5. **ห้าม fallback เลขพร้อมเพย์** ไม่ได้ตั้ง = ปิดปุ่ม QR + บอกว่าไปตั้งที่ไหน (หลักเดียวกับโทเคน LINE)
6. **ราคาทุน/กำไร ต้องไม่อยู่ใน payload ที่ส่งให้ role `bar`** — ซ่อนใน UI ไม่พอ
7. **ลูกค้าเป็นตัวเลือกเสมอ** — ไม่เลือกลูกค้าต้องขายได้ทุกเส้นทาง

## 3. เมนู — โหมดต้นทุน · หมวดหมู่ · การ์ดสูตร

### 3.1 โหมดต้นทุน 3 แบบ ← **ผู้ใช้แก้ดีไซน์ v2 (2026-09-10)**

| โหมด | เงื่อนไข | ตัดสต็อก | ต้นทุน | ใช้กับ |
|---|---|---|---|---|
| **A. มีสูตร** ← **ทางหลัก** | มีแถวใน `bar_recipe` | ✅ ตามสูตร | Σ(ปริมาณ × ต้นทุนถัวเฉลี่ย) | ค็อกเทล · ช็อต · ขายทั้งขวด · **กับแกล้มด้วย** |
| **B. ต้นทุนตายตัว** | ไม่มีสูตร แต่ตั้ง `fixed_cost` | ❌ | `fixed_cost` | ทางออกของจานที่ BOM ไม่คุ้มจะคีย์ |
| **C. ยังไม่ตั้ง** ← **ทางฉุกเฉิน** | ไม่มีทั้งคู่ | ❌ | 0 | คิวแน่นจนใส่สูตรไม่ทันจริง ๆ |

> 🔄 **ร่าง v2 ผมประเมินผิด แล้วผู้ใช้แก้ให้**
> ผมเขียนว่า *"ตอนยืนบาร์ลูกค้ารอ ไม่มีใครกรอกสูตรครบหรอก"* → ผู้ใช้ชี้ว่า
> **"พอผมทำเสร็จเสิร์ฟแล้วก็มากดสั่งเมนูแล้วใส่สูตรของแก้วนั้นไปเลย"**
> ★ เหตุผลที่ดีกว่าของผม: **คนชงคือคนที่รู้สูตรดีที่สุด ณ วินาทีนั้น** (ตวงอยู่กับมือ)
> ไม่ใช่ภาระ — เป็นจังหวะที่ข้อมูลสดที่สุดพอดี ⇒ **ได้ตัดสต็อกและรู้ต้นทุนทันที**
> เดิมผมวางให้โหมด C เป็นทางปกติ **ผิด** — มันต้องเป็นทางฉุกเฉิน
>
> ⚙️ **ผลต่อ UI**: ช่องใส่สูตรต้องกางรออยู่แล้วในฟอร์ม ＋เมนูใหม่ **ไม่ซ่อนหลังปุ่มอีกชั้น**
> และตัวเลือกวัตถุดิบต้อง **เรียงตามที่ใช้บ่อย/ใช้ล่าสุด** + พิมพ์กรองได้ + มีปุ่มลัดปริมาณ
> (15 / 30 / 45 / 60 ml) — นี่คือส่วนต่างระหว่าง *20 วินาที* กับ *2 นาที*
>
> 🚨 **โหมด C ยังต้องมีป้ายบนแถว** + แถบรวม *"เมนูที่ยังไม่ตั้งต้นทุน N รายการ"* ในแท็บเมนู
> ไม่มีแถบนี้ = ค้างตลอดกาลแล้วกำไรพองโดยไม่รู้ตัว

**กับแกล้ม**: ผู้ใช้ยืนยันว่าจะเลือกเฉพาะเมนูไม่ซับซ้อน (ยืนคนเดียว) **ตั้งใจใส่ BOM**
⇒ โหมด B เป็น **ทางออก ไม่ใช่ค่าปริยายของหมวดอาหาร**

### 3.2 หมวดหมู่ — เป็นแท็บในหน้าขาย

ตาราง `bar_category` (แก้ชื่อ/เรียงลำดับได้) · หน้า POS แสดง **1 แท็บต่อ 1 หมวด**
เมนูที่กด ＋เมนูใหม่ ตอนยืนบาร์ **ตกลงหมวด `custom` อัตโนมัติ** (ผู้ใช้สั่ง)

🪤 **แรงกดดันที่รู้ล่วงหน้า**: ผ่านไปครึ่งปี หมวด `custom` จะมีเป็นร้อยเมนู
⇒ แท็บ `custom` **เรียงตาม "สั่งล่าสุด / สั่งบ่อย" ไม่ใช่ตามตัวอักษร** + มีช่องค้นหา
**จงใจยังไม่เพิ่มธง "ซ่อนจากตะแกรง"** — ธงที่สองบนของชิ้นเดียวคือต้นทางของ
"ค่าเดียวมีสองนิยาม" (D81/D88/D91) · เพิ่มเมื่อเจอปัญหาจริง ไม่ใช่เดาไว้ก่อน

### 3.3 การ์ดสูตร — กดที่เมนูแล้วเห็นว่าชงยังไง

กดการ์ดเมนูในหน้าขาย → เปิดการ์ดที่บอก **ส่วนผสมครบทุกตัว + วิธีชง + แก้วที่ใช้ + หมายเหตุ**
🎯 นี่คือ *"เผื่อลูกค้ามาสั่งซ้ำจะได้เปิดดูได้ ให้จำเองคงไม่หมด"* ที่เป็นโจทย์ตั้งต้นของงานนี้

| ฟิลด์ | ชนิด | ตัวอย่าง |
|---|---|---|
| `method` | ข้อความหลายบรรทัด | *"shake 12 วิ · double strain · เหล้าบ๊วยลอยหน้า"* |
| `glass` | ข้อความสั้น + datalist ของที่เคยใช้ (แพตเทิร์น `SuggestInput` D72) | *"coupe"* · *"rocks"* · *"highball"* |
| `note` | ข้อความ | *"ของพี่โอ๊ต — ลดเวอร์มุท เพิ่มส้ม"* |

★ แยก `glass` ออกจาก `method` เพราะเป็นค่าสั้นที่ซ้ำกันเรื่อย ๆ → datalist ช่วยได้จริง
ส่วน `method` เป็นข้อความยาว ยัดเข้าโครงสร้างไม่คุ้ม

### 3.4 ฟิลเตอร์ "เมนูของลูกค้าคนนี้"

รวม 3 ความสัมพันธ์เข้าด้วยกัน (คำนวณที่ `lib/bar/menuFilter.ts` · golden **B9**):

| ความสัมพันธ์ | มาจาก |
|---|---|

## 4. เปิดบิลค้าง (A) — จุดที่กระทบมากที่สุด

### วงจรของบิล
```
เปิดบิล ──► เพิ่มรายการ (ตัดสต็อกทันที) ──► ... วนได้เรื่อย ๆ ...
   │                    │
   │                    └─► ยกเลิกรายการ (คืนสต็อก) — ทำได้อิสระระหว่างเปิด
   │
   └──► ปิดบิล: เลือกวิธีรับเงิน + ส่วนลด → พิมพ์
```

### 🚨 ตัดสต็อก ณ ตอน "สั่ง" ไม่ใช่ตอน "ปิดบิล"
เพราะ **เหล้าออกจากขวดตอนชงจริง** · ผลที่ได้:
- สต็อกบนจอถูกต้องตลอดคืน (ไม่ใช่กระโดดทีเดียวตอนตีสอง)
- บิลที่ลูกค้าหนีไม่จ่าย → ของก็หายไปจริง ๆ ซึ่ง **ถูกต้อง** (ยกเลิกบิลทั้งใบเมื่อไหร่ค่อยคืนสต็อก)
- ต้นทุนถูกแช่ ณ ตอนสั่ง ⇒ รับของแพงขึ้นระหว่างที่บิลยังเปิด ไม่ย้อนไปแก้แถวเก่า

### `bar_sale.status` 3 ค่า
`'เปิดอยู่'` → `'ปกติ'` (ปิดแล้ว) · หรือ → `'ยกเลิก'` (ทิ้งทั้งใบ คืนสต็อกทุกแถว)

### ป้ายชื่อบิล
`tab_name` เป็นข้อความอิสระ — *"โต๊ะ 3"* / *"พี่โอ๊ต"* / *"เคาน์เตอร์ซ้าย"* / ว่างก็ได้
หน้า POS มี **รายการบิลที่เปิดอยู่** ให้กดเข้าไปเพิ่มรายการ

### 🪤 บิลข้ามเที่ยงคืน — **รอบขาย `bar_day_start` + `bar_day_end`**

เปิด 23:50 ปิด 01:10 → ลงบัญชีวันไหน? ⇒ ตั้ง **รอบขาย** เป็นช่วงเวลา เช่น `18:00`–`03:00`

**กติกา (ตัดสินที่ `lib/bar/businessDate.ts` จุดเดียว ใช้ทั้งแดชบอร์ดและการลงบัญชี):**

| กรณี | `business_date` |
|---|---|
| ปิดบิล **ในรอบขาย** | = วันที่ที่รอบนั้น **เริ่ม** |
| ปิดบิล **นอกรอบขาย** | = วันที่ตามปฏิทินของ `closed_at` (ไม่ขยับ) |
| `start === end` (ค่าปริยาย `00:00`) | ถือว่า **ไม่ได้ตั้งรอบ** → ใช้วันที่ตามปฏิทินเสมอ = **พฤติกรรมเดิมเป๊ะ** |

ตัวอย่าง `18:00`–`03:00`:

| ปิดบิล | อยู่ในรอบ? | ลงวัน |
|---|---|---|
| ศุกร์ 23:50 | ✅ รอบที่เริ่มศุกร์ 18:00 | **ศุกร์** |
| เสาร์ 01:10 | ✅ รอบเดียวกัน | **ศุกร์** |
| เสาร์ 14:00 (ออกบูธกลางวัน) | ❌ นอกรอบ | **เสาร์** |

🚩 **คุณสมบัติที่ต้องรักษาไว้: ทุกเวลาต้องแมปไปวันใดวันหนึ่งเสมอ ห้ามมีบิลที่ไม่มีวัน**
นี่คือเหตุผลที่ *นอกรอบ* ไม่ใช่ error แต่ตกไปใช้วันตามปฏิทิน — ตั้งรอบไว้แล้วออกบูธกลางวัน
**ต้องขายได้ตามปกติ** ไม่ใช่โดนบล็อกหรือหายไปเฉย ๆ

🪤 **เคสที่กติกานี้ยังตอบไม่สวย**: ลากยาวถึงเสาร์ 04:00 (เลยรอบไป 1 ชม.) → ตกเป็นของวันเสาร์
ทั้งที่ใจคนคือหางของคืนวันศุกร์ ⇒ **ให้แก้ `business_date` รายบิลได้** (`bar.config` + เขียน `edit_log`)
เป็นทางออกของ 1% ที่ซื่อตรงกว่าการเดาให้

### ขายเร็วที่บูธ
`fn_bar_quick_sale` = เปิด+เพิ่ม+ปิด **ในทรานแซกชันเดียว** → ที่บูธคนต่อคิวยังกดทีเดียวจบ
เขียนแถวเหมือนกันเป๊ะกับเส้นทางเปิดบิลค้าง (ไม่มีข้อมูล 2 รูปแบบ)

## 5. แก้รายรายการหลังจ่าย (D) — 3 ระดับ

> ผู้ใช้สั่งว่า *"ดูผลกระทบต่อการบันทึกข้อมูลให้ดี"* ⇒ ยึดกติกาที่ระบบนี้ใช้อยู่แล้ว
> (D75 ค่าที่ยื่นแล้วต้องแช่ · D88 soft-void ไม่ลบ · D91 ปิดแล้วต้องถอนก่อน)

| สถานะบิล | แก้รายรายการ | ทำอะไร |
|---|---|---|
| **`เปิดอยู่`** | ✅ อิสระ | ยกเลิกแถว → คืนสต็อก · ยังไม่มีเอกสารและยังไม่มีเงิน |
| **`ปกติ` · ยังไม่ออกใบเสร็จ (BR) · ยังไม่ลงบัญชี** | ✅ ยกเลิกได้ทีละแถว (`bar.write`) | คืนสต็อก · ยอดบิลลดลง · เขียน `edit_log` + `bar_move` เหตุผล `'แก้บิล'` · **ขึ้นข้อความว่าต้องพิมพ์สลิปใหม่และคืนเงินลูกค้าเท่าไร** |
| **`ปกติ` · ออกใบเสร็จแล้ว **หรือ** ลงบัญชีแล้ว** | 🚨 **บล็อกที่ DB** | ใบเสร็จอยู่ในมือลูกค้าแล้ว / ตัวเลขเข้าบัญชีแล้ว → ต้อง **ยกเลิกทั้งบิลแล้วออกใหม่** · ปุ่มเป็นสีเทาพร้อมบอกว่าต้องกดอะไรแทน (D86: ซ่อนปุ่มแย่กว่าปุ่มเทา) |

🚨 **ห้ามลบแถวจริง** — `bar_sale_item.voided_at` + `void_reason` · `line_no` ไม่เรียงใหม่ (audit)
🚨 **ยอดบิลต้องคำนวณจากแถวที่ยังไม่ถูกยกเลิกเท่านั้น** และ `cost_total`/`grand_total` เขียนทับใหม่ตอนยกเลิกแถว

## 6. ทะเบียนลูกค้า (`bar_customer`)

### ทำอะไรได้
| ความสามารถ | ทำไมมีค่า |
|---|---|
| **เปิดการ์ดลูกค้า → เห็นทุกสูตรที่เคยสั่ง → กดสั่งซ้ำ** | 🎯 โจทย์ตั้งต้นของงานนี้ · แม่นกว่าการหวังว่าจะพิมพ์ชื่อโต๊ะเหมือนเดิมทุกครั้ง |
| **โน้ตที่ต้องจำ** — แพ้ถั่ว · ไม่กินหวาน · ชอบเปรี้ยวจัด | บาร์เทนเดอร์ที่จำได้คือเหตุผลที่ลูกค้ากลับมา |
| **เมนูโปรดปักหมุด** (`bar_customer_fav`) | *"ของประจำพี่โอ๊ต"* กดปุ่มเดียว |
| **ประวัติการมา** — กี่ครั้ง · ครั้งสุดท้ายเมื่อไร · ยอดสะสม | |
| **ค้นย้อนกลับ "ใครเคยสั่ง Negroni บ้าง"** | คิดเมนูใหม่แล้วรู้ว่าจะชวนใครมาลอง |
| **รายชื่อคนที่ไม่ได้มานาน** | |
| **ออกใบเสร็จในนามบริษัทลูกค้า** (`tax_id`) | ลูกค้าที่พาแขกมาเลี้ยง |

### กติกา
- 🚨 **ลูกค้าเป็นตัวเลือกเสมอ** — ที่บูธเจอกันครั้งเดียว ไม่มีใครยอมให้เบอร์ · ไม่เลือกต้องขายได้ปกติทุกเส้นทาง
- ⚠️ **PDPA**: เบอร์โทร = ข้อมูลส่วนบุคคล → ต้องมีปุ่มลบจริง (กติกา CLAUDE.md ครอบอยู่แล้ว) และหน้าจอบอกตรง ๆ ว่าเก็บอะไรไว้
- `visits` / `spend_total` / `last_seen` **อัปเดตตอนปิดบิล** และ **ถอยกลับเมื่อยกเลิกบิล**

### 🔴 ทำไมต้องแยกจาก `contacts` — ตรวจของจริงแล้ว (2026-09-10)

ผู้ใช้ถามว่า *"ตอนนี้เก็บข้อมูลลูกค้าแยก EID ไหม"* → **ไม่แยก** และแรงกว่านั้น:

| ข้อเท็จจริง | หลักฐาน |
|---|---|
| `contacts` **มี** คอลัมน์ `entity_id` | 0026 backfill ทุกแถวเป็นกิจการหลัก |
| แต่ **PK ไม่มี `entity_id`** | `0027:58` → `(tenant_id, contact_id)` · คอมเมนต์เขียนเองว่า *"master ของลูกค้า = (tenant_id, คีย์)"* |
| unique ชื่อ+สาขา **เป็นระดับ tenant ไม่ใช่ entity** | `0027:112` `contacts_name_branch_norm (tenant_id, lower(name), branch)` |
| 🚨 **ไม่มีโค้ดฝั่งอ่านจุดไหนกรอง `entity_id` เลยสักจุด** | grep `.from("contacts")` 11 จุด — กรอง entity **0 จุด** |

⇒ **`contacts.entity_id` เป็นคอลัมน์ที่มีอยู่แต่ไม่มีใครอ่าน** — ตระกูลเดียวกับ `employees.end_date` (D76)
และ `pay_components.expense_cat` (D67) ที่ต้องลบทิ้ง · ทะเบียนคู่ค้าวันนี้ **ใช้ร่วมกันทั้ง tenant**

**ผลที่ตามมาถ้าเอา `/bar` ไปใช้ `contacts`:**
1. 🔴 role `bar` (พนักงานบาร์) จะ **เห็นทะเบียนลูกค้าค้าส่งทั้งหมดของโรงกลั่น** พร้อมเลขภาษี ที่อยู่ เครดิตเทอม
2. ชื่อซ้ำข้ามกิจการไม่ได้ — ลูกค้าบาร์ชื่อ "สมชาย" ชนกับคู่ค้า B2B ชื่อเดียวกัน
3. ทะเบียนคู่ค้า B2B จะถูกเจือด้วยชื่อขาจรคืนละหลายสิบคน

⇒ **`bar_customer` แยกต่างหาก** (หลักเดียวกับที่ `employees` แยกจาก `contacts` ใน D66)

### ถ้าบาร์จด VAT แล้วลูกค้าขอใบกำกับ

`bar_customer` ต้องมี **ชื่อ · ที่อยู่ · เลขประจำตัวผู้เสียภาษี · สาขา** ครบ (ใบกำกับต้องมีของผู้ซื้อทั้งสี่)

⇒ **ย้ายไป `lib/shared/taxCustomer.ts` แล้วให้ `lib/sales/customer.ts` re-export ต่อ**

> ไม่ใช่ปล่อยเมนูลอย · และ `is_system` กัน `custom` หายไป (เป็นที่ลงจอดของเมนูใหม่)

### โฟลว์หน้า POS
```
[บิลที่เปิดอยู่: โต๊ะ3 · พี่โอ๊ต · +เปิดบิลใหม่]
   ↓ เลือกบิล  (เลือกลูกค้าได้ตอนเปิด)
[ค็อกเทล][ช็อต][ขวด][อาหาร][custom]   ← แท็บหมวด
[ ] เฉพาะของ พี่โอ๊ต                    ← ชิปกรอง (โผล่เมื่อบิลนี้มีลูกค้า)
   ↓ กดการ์ดเมนู → เห็นสูตร + วิธีชง + แก้ว → ยืนยัน
เพิ่มเข้าบิล (ตัดสต็อกทันที) → ...สั่งเพิ่มได้เรื่อย ๆ...
   │
   └─► ＋เมนูใหม่: ชื่อ + ราคา + **สูตรกางรออยู่แล้ว** + วิธีชง + แก้ว
        → บันทึก (ลงหมวด custom · ผูกกับลูกค้าที่เลือกอยู่) → เข้าตะกร้าทันที
   ↓ ลูกค้าเรียกเช็คบิล → ใส่ส่วนลด → กด "เช็คบิล"
พิมพ์ ใบแจ้งรายการ + QR ยอดเป๊ะ   (บิลยังเป็น 'เปิดอยู่')
   ↓ ลูกค้าสแกนจ่าย / จ่ายสด / รูดบัตร
เลือกวิธีรับเงิน → กด "ยืนยันรับเงินแล้ว" → ปิดบิล
```
🚨 ปุ่มต้องเขียน **"ยืนยันรับเงินแล้ว"** ไม่ใช่ "ตรวจสอบการชำระเงิน" — ระบบไม่ได้ตรวจอะไรเลย
★ **QR ยังขึ้นบนจอด้วย** (กระดาษหมด/ลูกค้าอยากสแกนจากจอ) — แค่ไม่ใช่ทางหลักอีกต่อไป
🪤 สั่งเพิ่มหลังเช็คบิลแล้ว = **พิมพ์ใหม่** (ยอดเปลี่ยน QR ต้องเปลี่ยนตาม) · ใบเก่ากลายเป็นขยะทันที
   ⇒ ใบแจ้งรายการต้องมี **เวลาที่พิมพ์** เสมอ เพื่อให้รู้ว่าใบไหนใหม่กว่า

## 14. พิมพ์ 80 มม. + **QR บนใบแจ้งรายการ** ← แก้จาก v2 ตามที่ผู้ใช้สั่ง

- `@page { size: 80mm auto; margin: 0 }` · เนื้อกว้าง `72mm` · ฟอนต์ไทย self-host เดิม (D42)
- พิมพ์ผ่าน `window.print()` → RawBT (**เทสผ่านแล้ว**)
- 🚫 **ไม่พิมพ์ป้ายช่องทาง/งาน ลงบิล** (ผู้ใช้สั่ง — ใช้ดูรายงานอย่างเดียว)

### เอกสาร 3 ชนิด

| ชนิด | ออกเมื่อไร | มี QR? | เลข |
|---|---|---|---|
| **ใบแจ้งรายการ (ยังไม่ชำระ)** | ลูกค้าเรียกเช็คบิล · บิลยัง `เปิดอยู่` | ✅ **มี QR ยอดเป๊ะ** | `B…` |
| **ใบแจ้งรายการ (ชำระแล้ว)** | พิมพ์ซ้ำหลังปิดบิล | 🚫 **ไม่มี** + ประทับ *ชำระแล้ว · วิธี · เวลา* | `B…` เดิม |
| **ใบเสร็จรับเงิน** | กดออกเมื่อลูกค้าขอ | 🚫 **ไม่มีเด็ดขาด** | `BR…` |

### 🚨 กติกาข้อเดียวที่ห้ามพลาด — QR บนกระดาษที่จ่ายแล้ว = ลูกค้าจ่ายซ้ำ

QR บนจอหายไปเองเมื่อปิดหน้า แต่ **กระดาษอยู่กับลูกค้าตลอดไป**
ถ้าใบที่ปิดบิลแล้วยังมี QR ติดอยู่ ลูกค้าหยิบมาสแกนอีกทีคืนหน้า = **โอนเงินซ้ำโดยไม่มีอะไรกัน**
⇒ **`hasQr` ตัดสินจาก `status === 'เปิดอยู่'` เท่านั้น ตัดสินใน `lib/bar/receipt.ts` จุดเดียว มี golden คุม**
(ตระกูลเดียวกับ D91/0059 — ตรรกะถูกแต่กระดาษบอกอีกอย่าง)

### 🪤 QR บนกระดาษความร้อน

- เครื่อง 203 dpi · กระดาษ 80 มม. พิมพ์ได้จริง ~72 มม. ≈ **576 dot**
- QR ควรกว้าง **~25 มม. (≈200 dot)** — เล็กกว่านี้กล้องมือถือจับยากบนกระดาษความร้อนที่ contrast ต่ำ
- ต้องมี **quiet zone ขาวรอบ ๆ อย่างน้อย 4 โมดูล** ไม่งั้นสแกนไม่ติด
- `image-rendering: pixelated` — ปล่อยให้เบราว์เซอร์ปรับ antialiasing เอง = ขอบเบลอ สแกนพลาด
- 🚩 **ต้องพิสูจน์ด้วยการพิมพ์จริงแล้วสแกนด้วยแอปธนาคารจริง** — `build`/`lint`/`test` มองไม่เห็นเรื่องนี้เลย (บทเรียน D94 ที่ต้องเรนเดอร์ PDF จริงส่งให้ผู้ใช้ดู 2 รอบ)

### เรื่องอากรแสตมป์ — อธิบายให้ชัด และ **มันไม่บล็อกงานนี้**

ประมวลรัษฎากรกำหนดว่า **"ใบรับ" ตั้งแต่ 200 บาทขึ้นไป ต้องติดอากรแสตมป์ 1 บาท**
"ใบรับ" = เอกสารที่เขียนว่ารับเงินแล้ว (ใบเสร็จรับเงิน) · **ไม่ใช่** ใบแจ้งรายการที่บอกว่าต้องจ่ายเท่าไร

⇒ **ดีไซน์นี้เลี่ยงประเด็นไปเองอยู่แล้ว**: ทุกบิลได้ *ใบแจ้งรายการ* (ไม่ใช่ใบรับ)
ส่วน *ใบเสร็จรับเงิน* ออกเฉพาะที่ลูกค้าขอ ซึ่งคืนหนึ่งอาจจะไม่มีสักใบ
⚠️ **ผมไม่ใช่ที่ปรึกษาภาษี** — ถามผู้ทำบัญชียืนยันตอนใกล้เปิดบาร์ ไม่ต้องรอคำตอบก่อนเริ่มงาน

## 23. รื้อโฟลว์แท็บขาย (งานหลักของรอบนี้)

### 23.1 วินิจฉัย

ปัญหาไม่ใช่ "ยังไม่ได้ทำ responsive" แต่เป็น**ผังหน้าเดียวที่ผิดทั้งบนจอกว้างและจอแคบ ด้วยคนละเหตุผล**

- **จอแคบ** — `lg:grid-cols-[1fr_360px]` ยุบเป็นคอลัมน์เดียว ⇒ ลำดับบนจอคือ *บิล → ตารางเมนูทั้งหมด → (เลื่อนลงไปไกล) → ตะกร้า*
  กดเมนูแล้ว **ไม่มีอะไรขยับในสายตา** เพราะสิ่งที่เปลี่ยนอยู่นอกจอ
- **จอกว้าง** — คอลัมน์ขวาถูกตรึง 360px แล้วยัด *ในบิล + รอส่ง + ยอด + วิธีจ่าย + 3 ปุ่ม* ลงไปทั้งหมด
  แถวตะกร้าใช้ `flex-wrap` เลยแตกบรรทัดเองไม่เป็นระเบียบ · ต้องเลื่อนในคอลัมน์แคบทั้งที่ฝั่งซ้ายว่างครึ่งจอ
- **ทั้งสองจอ** — มี 2 ลิสต์ที่หน้าตาคล้ายกัน (*สั่งไปแล้ว* / *กำลังจะสั่ง*) วางติดกันในกล่องเดียว
  ลิสต์บนแก้ไม่ได้ ลิสต์ล่างแก้ได้ **โดยไม่มีอะไรอธิบายว่าทำไม**
- แถวในลิสต์ล่างคือ `[ช่องตัวเลข] ชื่อเมนู [ช่องตัวเลข] ☐แถม [ยอด]` — **ช่องตัวเลขเปล่า 2 ช่องติดกันไม่มีป้าย**
  (มีแค่ `title=` ซึ่งบนทัชสกรีนไม่มีทางเห็น และบนคอมต้องเอาเมาส์ไปค้าง)

### 23.4 แถวในถาด

```
[−]  2  [+]   Negroni                         ฿520   ⋯
```

- ปุ่ม **−/+** แทนช่องกรอก → นิ้วโป้งกดง่าย **และแก้เรื่อง 0 ค้างไปในตัว** (ไม่มีช่องให้ค้าง)
  กดเลขตรงกลางถึงจะเปิดช่องพิมพ์ (สำหรับสั่ง 12 แก้วรวด)
- **⋯** กางออกมาเป็น: ส่วนลด `[บาท|%]` `[ค่า]` · ☐ แถม · ปุ่มลบบรรทัด
  ⇒ 95% ของเวลาไม่ต้องเห็นมัน แต่ **ยังอยู่ที่เดิมเสมอ ไม่ใช่ซ่อนแบบเดาไม่ได้**
- **⋯ ที่กางอยู่ต้องมีร่องรอยบนแถวที่ยุบแล้ว** — ถ้าลด 10% ไว้ แถวยุบต้องขึ้น `−10%` ตัวเล็ก
  🪤 ไม่งั้นส่วนลดที่ตั้งไว้จะหายจากสายตาแล้วปิดบิลผิดยอด (ตระกูล D80: ค่าที่มีผลจริงต้องมองเห็น)

### 23.6 จอเก็บเงินแยกออกมา

ปุ่มเดียวใต้ตะกร้า: **`เก็บเงิน ฿520`** → เปิดจอเก็บเงินเต็มหน้า เรียงตามลำดับที่เกิดจริงหน้าเคาน์เตอร์

1. สรุปยอด + ส่วนลดท้ายบิล (`บาท | %`)
2. วิธีรับเงิน (ปุ่มใหญ่ 4 ปุ่ม ไม่ใช่ dropdown)
3. **QR เต็มจอ** (เลือกโอน/QR) — ปุ่ม *พิมพ์ใบแจ้งรายการ* อยู่ข้าง ๆ
4. **ยืนยันรับเงินแล้ว → ปิดบิล**
5. หลังปิด: *พิมพ์ซ้ำ* · *ลูกค้าขอใบเสร็จ* · *ลูกค้าขอใบกำกับเต็มรูป* (เฉพาะกิจการจด VAT — ดูข้อ 25)

🚨 ข้อความ *"ระบบไม่ได้ตรวจสอบว่าเงินเข้าจริง"* **ต้องอยู่ติดปุ่มยืนยันเสมอ** — PromptPay ไม่มี callback

### 23.7 โหมดบูธ (ขายเร็ว)

สวิตช์บนหัวแท็บขาย — เปิดแล้ว:
- ไม่มีรายการบิล ไม่มีชื่อโต๊ะ (บูธไม่มีใครค้างบิล)
- กดเมนู → ถาด → ปุ่มเดียว **`รับเงิน`** → จอเก็บเงิน → จบ
- เรียก `fn_bar_quick_sale` (**มีอยู่แล้วตั้งแต่ 0065 แต่ยังไม่มีปุ่มเรียกเลยสักที่**)
  ★ RPC ตัวนี้เขียนแถวเหมือนเส้นทางเปิดบิลค้างเป๊ะ ⇒ **รายงานไม่ต้องรู้ว่าขายมาจากโหมดไหน**
- จำสถานะสวิตช์ไว้ต่อเครื่อง (`localStorage`) **ไม่ใช่ `app_settings`** — เครื่องที่บาร์กับเครื่องที่บูธคือคนละโหมดในวันเดียวกันได้

### 23.8 เมนูที่กดไม่ได้ต้องบอกว่าทำไม

ตอนนี้ยังไม่เลือกบิล = การ์ดเมนูเทาหมดเฉย ๆ → ต้องมี `<MissingHint>` *"เปิดบิลก่อนถึงจะสั่งได้"* (กติกา D83 ที่เราตั้งเอง)

## 24. ส่วนลดเป็น % (แตะชั้นสูตร — golden B4)

### กติกาที่ล็อก

| | คิดจากอะไร |
|---|---|
| **% ต่อรายการ** | `ราคา × จำนวน` ของบรรทัดนั้น |
| **% ท้ายบิล** | ยอด**หลัง**หักส่วนลดรายรายการแล้ว (= `subTotal`) **ไม่ใช่จากราคาเต็ม** |

🚨 **แปลง % เป็นบาทก่อนเข้าท่อคำนวณเดิมเสมอ** ⇒ ลำดับใน `barTotals()` ไม่ขยับแม้บรรทัดเดียว
⇒ **golden B4 ต้องผ่านโดยไม่แก้ไฟล์เทส** (หลักฐานว่าเส้นทางเดิมไม่กระทบ — แพตเทิร์น D55/D69/D81)

### เก็บอะไรลง DB

- **เงินคือค่าที่แช่ไว้** — `bar_sale.discount` / `bar_sale_item.line_discount` ยังเป็น **บาท** เหมือนเดิม
- เพิ่ม `discount_pct` / `line_discount_pct` **nullable · เพื่อพิมพ์บนสลิปว่า "ลด 10%" เท่านั้น**
- 🚨 **ห้ามคิด % สดตอนเปิดดูย้อนหลัง** — ราคาเมนูเปลี่ยนวันหลัง แล้วส่วนลดของบิลเก่าจะขยับตาม
  = ยอดที่ลงบัญชีไปแล้วเพี้ยน (กติกา D75: ชื่อ = ค่าปัจจุบัน · **ตัวเงิน = ค่าที่แช่ไว้**)

### เทส golden **B10** (`lib/bar/discount.ts`)

- 10% ของ 520 = 52.00 · ปัด 2 ตำแหน่งทุกขั้น
- % เกิน 100 → ตัดที่ 100 (ยอดสุทธิเป็น 0 **ไม่ใช่ติดลบ**)
- % ติดลบ → ปฏิเสธ
- **ทิศตรงข้าม**: ลด 10% ต่อรายการ + 10% ท้ายบิล ≠ ลด 20% (พิสูจน์ว่าฐานต่างกันจริง)
- ของแถม (`isComp`) → % ไม่มีผล ยอดเป็น 0 อยู่แล้ว

### migration **0068**

`bar_sale.discount_pct` · `bar_sale_item.line_discount_pct` · `fn_bar_add_lines`/`fn_bar_close_sale` รับพารามิเตอร์เพิ่ม
🪤 **พารามิเตอร์เพิ่ม = ต้อง `drop function` ก่อน** (D69) · 🚨 SQL ยังต้องบังคับ `comp → 0` และ `ติดลบ → 0` เหมือน 0066

## 25. VAT ครบวง (ผู้ใช้ตอบว่า "จด/อาจจะจด")

### 25.1 ราคาหน้าบาร์เป็นราคารวม VAT

`lib/bar/vat.ts` — golden **B11**

```
vat  = round2(gross × 7 / 107)
base = round2(gross − vat)
```

🚨 ถอดจาก **ยอดสุทธิหลังส่วนลดและปัดเศษแล้ว** ไม่ใช่จาก `subTotal`

### 25.2 สลิปเปลี่ยนหน้าตาเมื่อกิจการจด VAT

- หัวกระดาษ: **"ใบเสร็จรับเงิน/ใบกำกับภาษีอย่างย่อ"**
- เพิ่ม 3 บรรทัด: ยอดก่อนภาษี · ภาษีมูลค่าเพิ่ม 7% · ยอดรวม
- ต้องมีเลขประจำตัวผู้เสียภาษีผู้ขาย + เลขที่เอกสาร + วันที่ **เสมอ**
- 🚨 บรรทัดเหล่านี้ **ปิดไม่ได้** ในหน้า customize (ดูข้อ 27)

### 25.3 🔴 เลขใบกำกับอย่างย่อต้องมีทุกใบ ไม่ใช่ออกตามคำขอ

วันนี้ `rcpt_no` (`BR…`) ออกเมื่อลูกค้าขอเท่านั้น — **ใช้กับ VAT ไม่ได้**
กิจการจด VAT ต้องออกใบกำกับอย่างย่อ**ทุกครั้งที่ขาย** ⇒ เมื่อ `entities.is_vat = true`:

- `fn_bar_close_sale` ออกเลขให้ทันทีที่ปิดบิล (ชุด `BR` เดิม เดินต่อเนื่องต่อ entity)
- ปุ่ม *ลูกค้าขอใบเสร็จ* กลายเป็น *พิมพ์ซ้ำ* (เพราะออกไปแล้ว)
- 🚨 **กิจการไม่จด VAT พฤติกรรมเดิมทุกประการ** — ออกตามคำขอเหมือนเดิม · มีเทสล็อกทั้งสองทิศ

### 25.4 ลูกค้าขอใบกำกับเต็มรูป

ต้องมีของผู้ซื้อครบ 4 อย่าง (ชื่อ · ที่อยู่ · เลขภาษี · สาขา) — `bar_customer` มีช่องครบแล้วตั้งแต่ 0064

- ปุ่มเทา + บอกว่าขาดอะไร ถ้ากรอกไม่ครบ (`missingText()` D83)
- 🚨 **หนึ่งบิลออกได้ใบเดียว** — ออกเต็มรูปแล้วใบย่อของบิลนั้นเป็นโมฆะ ต้องบันทึกว่าออกอะไรไป
- บิลที่ออกเต็มรูป **แยกเป็น `transactions` ของตัวเอง 1 แถว พร้อม `contact`** และ**ถูกกันออกจากยอดรวมรายวัน** (ไม่งั้นนับซ้ำ)

### 25.5 `fn_bar_post_day` ต้องเขียนช่องภาษีให้ถูก — แก้ B-4

ยืนยันจาก `calc.ts:taxReport()` แล้วว่า ภพ.30 ใช้ `amount_after_discount` เป็น**ฐานก่อนภาษี** แล้วคิด 7% จากผลรวม

| ช่อง | ไม่จด VAT | จด VAT |
|---|---|---|
| `base_amount` / `amount_after_discount` | ยอดรวม | **ยอดก่อนภาษี** |
| `vat_amount` | 0 | **ภาษี** |
| `net_amount` | ยอดรวม | ยอดรวม (เงินที่รับจริง) |
| `tax_invoice_no` | — | **ช่วงเลขใบย่อของวันนั้น** เช่น `BR260913-001 ถึง BR260913-047` |

+ เตือนเรื่อง `taxAccounts` ตามข้อ 22

**เทส `tests/tenant/bar-vat.test.ts`**: ปิดบิล 3 ใบในกิจการจด VAT → ลงบัญชี → เรียก ภพ.30 ของเดือนนั้น
**ต้องเห็นยอดบาร์และ VAT ตรงกับที่พิมพ์บนสลิป** · แล้วทำซ้ำกับกิจการไม่จด VAT → **ต้องไม่โผล่ใน ภพ.30 เลย**
🔴 นี่คือชั้นเดียวที่มองเห็นตรรกะใน plpgsql (บทเรียน D79)

### 25.6 ⚠️ ที่ต้องถามผู้ทำบัญชี (ไม่บล็อกงาน)

**การใช้เครื่อง POS ออกใบกำกับภาษีอย่างย่อต้องยื่นขออนุมัติสรรพากรก่อน** — ผมไม่ใช่ที่ปรึกษาภาษี
ระบบจะพร้อมออกให้ แต่**คนต้องไปขออนุมัติเอง** → ลง `docs/GOLIVE_CHECKLIST.md`

## 26. ลงบัญชี — ตั้งค่า + ตามเก็บ + เตือน LINE (ผู้ใช้เลือกทาง **ข.**)

### 26.1 การ์ดใหม่ในแท็บตั้งค่าบาร์ — แก้ B-3

- **บัญชีที่รายได้บาร์เข้า** — dropdown จาก `bank_accounts` (ไม่ใช่ช่องพิมพ์) + เตือนถ้าไม่ได้ติ๊กเป็นบัญชี ภพ.30
- **หมวดรายรับ** — `SuggestInput` พิมพ์เองได้ + datalist จากหมวดที่เคยใช้ (ค่าปริยาย `รายได้บาร์`)
- 🪤 **แยก action จากการ์ดกิจการ** — dropdown ตัวเดียวทำ 2 หน้าที่คือกับดัก D63/D80
- ซ่อนทั้งการ์ดเมื่อโมดูล `accounting` ไม่ได้เปิด (บาร์ต้องขายแยกได้ — แผนข้อ 8)

### 26.2 แถบตามเก็บบนแดชบอร์ด

```
ยังไม่ได้ลงบัญชี 3 วัน (10, 11, 12 ก.ย.) · รวม ฿4,280   [ลงบัญชีทั้งหมด]
```

- ไล่จาก `bar_sale` ที่ `status='ปกติ'` และไม่มีแถว `bar_post` ที่ยังไม่ถูกถอน
- 🚨 **นับเฉพาะวันที่ผ่านรอบขายไปแล้ว** — คืนนี้ที่ยังขายอยู่ต้องไม่ขึ้นเตือน
- กดทีเดียวลงย้อนหลังได้ทุกวัน **แต่ยิงทีละวัน** และรายงานผลรายวัน (วันหนึ่งล้มต้องไม่ล้มทั้งก้อน)

### 26.3 เตือน LINE

**เพิ่มผู้เข้าร่วมรายที่สามในระบบเดิม ไม่ได้สร้างของใหม่** — cron เดิม · `sendLineToTenant()` เดิม · `CRON_SECRET` เดิม · ไม่ต้องแตะ `vercel.json`

- 🚨 **แยกเป็น `barPart()` เรียกด้วยธงโมดูล `bar` ของตัวเอง — ห้ามเอาไปต่อท้ายลูปเดิม**
  `taxPart()`/`excisePart()` มี `continue` หลายจุด **งานใหม่จะถูกข้ามเงียบ ๆ และ TS มองไม่เห็น** (บทเรียน D92)
- 🚨 **ไม่บอกยอดเงิน** — บอกแค่ว่ามีกี่วันที่ยังไม่ลงบัญชี (กติกา D88 · ข้อความ LINE เข้ากลุ่มได้)
- 🚨 **ส่งก่อนแล้วค่อยจด** — จดก่อนแล้วส่งพลาด = เตือนหายตลอดกาล
- กันซ้ำด้วย `integration_log` (`action = 'bar_post_reminder'`) = **ครั้งเดียวต่อวัน**
- ไม่มีวันค้าง → **เงียบ** (ไม่ส่ง "ทุกอย่างเรียบร้อย" — สแปมทำให้คนเลิกอ่าน)

**ไม่ทำ auto-post** เพราะบิลที่ยังเปิดค้างตอนตี 3 จะถูกทิ้งนอกยอดโดยไม่มีใครรู้ และวันที่ถูกลงบัญชีเองจะยกเลิกบิลไม่ได้ทันทีโดยผู้ใช้ไม่ได้สั่ง

## 27. customize บิล

### 27.1 เก็บที่ไหน

**`app_settings` kind เดียว `bar_receipt_layout` เก็บ JSON ทั้งก้อน**
🪤 ไม่แตกเป็น kind ละสวิตช์ เพราะ `app_settings.kind` เป็น CHECK whitelist ที่ต้องยกรายชื่อเดิมมาเขียนทับทั้งก้อนทุกครั้ง (D80) — เพิ่มสวิตช์ทีหลังจะต้องลง migration ทุกรอบ

### 27.2 ปรับอะไรได้

| กลุ่ม | รายการ |
|---|---|
| **เปิด/ปิด** | ที่อยู่ · เลขภาษี · โทร · เวลาที่พิมพ์ · ชื่อลูกค้า · สรุปของแถม · **ป้ายช่องทาง/งาน (ปริยายปิด)** |
| **ลำดับ** | ▲▼ สลับลำดับบล็อก — **ไม่ใช้ drag** (ทัชสกรีนชนกับการเลื่อนหน้า · และ D70 แก้โจทย์นี้ด้วย ▲▼ ไปแล้ว ไม่ต้องเพิ่ม library) |
| **ข้อความ** | หัวบิล 2 บรรทัด · ท้ายบิล (มีแล้ว) · แทรกตัวแปรได้ `{ชื่อร้าน} {เลขบิล} {ยอด} {วันที่} {ชื่อลูกค้า}` |
| **โลโก้** | อัปโหลดเข้า Storage · แปลงเป็นขาวดำ 1-bit ตอนอัปโหลด **แล้วโชว์ผลลัพธ์ให้ดูก่อนบันทึก** (203dpi ขาวดำล้วน ภาพสีเทาจะออกมาเป็นด่าง) |
| **กระดาษ** | 80 มม. (ปริยาย) / **58 มม.** — ต้องย่อ QR ตามและยังต้อง ≥25 มม. |
| **ฟอนต์** | ปกติ / ใหญ่ |

### 27.3 กติกาที่ขาดไม่ได้

**① พรีวิวสดขนาดเท่ากระดาษจริง** เรนเดอร์ด้วย `receiptHtml()` **ตัวเดียวกับที่พิมพ์จริง**
🚨 ห้ามวาดจำลอง — พรีวิวที่ไม่ตรงกระดาษแย่กว่าไม่มีพรีวิว · สลับดูได้ทั้ง *ใบแจ้งรายการ (มี QR)* · *ใบเสร็จ* · *แบบจด VAT*

**② บรรทัดที่กฎหมายบังคับ ปิดไม่ได้ — และต้องบอกว่าทำไม**
เมื่อ `is_vat = true`: ชื่อผู้ขาย · ที่อยู่ · เลขประจำตัวผู้เสียภาษี · เลขที่เอกสาร · ยอด VAT · คำว่า *ใบกำกับภาษีอย่างย่อ*
→ **สวิตช์เทาพร้อมเหตุผล ไม่ใช่หายไป** (D86: ปุ่มเทาดีกว่าซ่อนปุ่ม)
ปล่อยให้ปิดได้ = ออกใบกำกับที่ใช้ไม่ได้ตามกฎหมายทั้งคืนโดยไม่มีอะไรฟ้อง

**③ QR ยังตัดสินที่ `receipt.ts` จุดเดียว** — ตั้งค่า*ปิด* QR ได้ แต่ **เปิดบนใบที่จ่ายแล้วไม่ได้เด็ดขาด**
(กระดาษอยู่กับลูกค้าตลอดไป — หยิบมาสแกนคืนถัดไป = โอนซ้ำ)

**④ ตัวแปรในข้อความเป็นชุดปิด กดปุ่มแทรกอย่างเดียว**
🚨 ห้ามมีเงื่อนไข ห้ามมีสูตร ห้ามให้พิมพ์ชื่อตัวแปรเอง — ไม่งั้นซ้ำรอย "ห้ามทำภาษาสูตร" (D67/D70)
ตัวแปรที่สะกดผิดต้องพิมพ์ออกมาเป็นตัวอักษรตามเดิม **ห้ามพิมพ์ว่า `undefined`**

**⑤ `Record<BlockKey, …>` บังคับความครบ**
เพิ่มบล็อกใหม่วันหลังแล้วลืมเติมลิสต์ลำดับ = **บล็อกนั้นหายจากกระดาษโดยไม่มี error** (D84)

### 27.4 เทส

- สลับลำดับทุกแบบแล้ว **เนื้อหาต้องครบเท่าเดิมทุกบล็อก** (เทียบจำนวน/ข้อความ ไม่ใช่เทียบ HTML)
- `is_vat = true` + ปิดทุกสวิตช์ที่ปิดได้ → บรรทัดบังคับ 6 อย่างยังอยู่ครบ
- ตัวแปรที่ไม่รู้จัก → คงข้อความเดิม
- 58 มม. → QR ยังกว้าง ≥ 25 มม.

และ `fn_bar_post_day` เดิม **ไม่เคยเซ็ต `vat_amount` เลย** ⇒ บาร์ที่จด VAT ยื่นภาษีขายขาด

### golden **B11** (`lib/bar/vat.ts` · 10 เทส)

🚨 **`base` คิดด้วยการ *ลบ* ไม่ใช่สูตรของตัวเอง** — `round2(g×100/107)` กับ `round2(g×7/107)`
บวกกันแล้วคลาดจาก `gross` ได้ 1 สตางค์ ⇒ บนกระดาษจะมีใบที่ `242.99 + 17.02 = 260.01`
ซึ่งลูกค้าอ่านแล้วจับได้ทันที · เทสไล่ยอดทุก 7 สตางค์ตั้งแต่ 0.01 ถึง 5,000 บาท
ยืนยัน **`base + vat = gross` เสมอ**

🚨 ถอดจาก **ยอดสุทธิหลังส่วนลดและปัดเศษ** — ถอดจาก `subTotal` = ภาษีขายที่ยื่นสูงกว่าเงินที่รับจริง

### สิ่งที่เปลี่ยนเมื่อ `entities.is_vat = true` (และ **เฉพาะ** ตอนนั้น)

| | ไม่จด VAT (เดิม) | จด VAT |
|---|---|---|
| หัวใบเสร็จ | ใบเสร็จรับเงิน | **ใบเสร็จรับเงิน/ใบกำกับภาษีอย่างย่อ** |
| ท้ายสลิป | ยอดสุทธิ | + **ยอดก่อนภาษี · ภาษีมูลค่าเพิ่ม 7%** |
| เลขเอกสาร | ออกเมื่อลูกค้าขอ | **ออกให้ตั้งแต่ปิดบิล** |
| ปุ่ม *ลูกค้าขอใบเสร็จ* | อยู่ | **หายไป** (ออกให้แล้ว — ปุ่มที่กดแล้วไม่มีอะไรเกิด = คนสงสัยว่าพัง) |
| `transactions` | ฐาน = ยอดเต็ม · `vat_amount` 0 | ฐาน = **ยอดก่อนภาษี** · `vat_amount` · `tax_invoice_no` = **ช่วงเลข BR ของวันนั้น** |

🚨 **ไม่ส่ง `isVat` มา = ถือว่าไม่จด** — เดาว่าจดแล้วออกใบกำกับให้คนที่ไม่ได้จดคือความผิด
