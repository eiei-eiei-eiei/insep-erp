## 0. เป้าหมาย (ผู้ใช้กำหนด)

- **ในกิจการเดียวกัน** ขาย · ผลิต · บัญชี · บาร์ · เงินเดือน ลิงก์กันเหมือนวันนี้ทุกจุด (ส่งของ → ตัดสต็อก → ภส. · บิลต้นทุน → วัตถุดิบ · บาร์/ขาย/เงินเดือน → ลงบัญชี)
- **ข้ามกิจการ ไม่มีลิงก์สด** — มีแค่ปุ่มของเจ้าของในหน้าตั้งค่า "นำเข้าจากอีกกิจการ" (คัดลอกของตั้งต้น ไม่ใช่ธุรกรรม)
- ล็อกอินเดียว สลับกิจการได้จากแถบบน
- ขนาดที่ผู้ใช้ยอมรับ: 8–12 session

## 1. หลักการเดียวที่ทุกเฟสต้องยึด

> **"ลืมกรอง = มองไม่เห็น" ไม่ใช่ "ลืมกรอง = ข้อมูลปน"**

วันนี้ชั้นแยก tenant ปลอดภัยเพราะ DB กรองเอง (RLS + ค่าปริยาย `my_tenant()`) — โค้ดลืมกรองก็ไม่เห็นของคนอื่น
แต่ชั้นแยกกิจการของผลิต/ขาย/เงินเดือน อยู่ที่ "โค้ดต้องจำกรองเอง" (ตัวอย่างจริง: ฟอร์ม ภส. ที่ D186 เพิ่งแก้)
ทาง Y จึงต้องย้ายการแยกกิจการลงไปที่ DB **แพตเทิร์นเดียวกับ tenant ทุกประการ**:

| ชั้น | tenant (มีแล้ว) | กิจการ (ทาง Y) |
|---|---|---|
| ค่าที่ session ถืออยู่ | `my_tenant()` จาก profile | `my_current_entity()` (ส่วนที่ 2) |
| ค่าปริยายตอน INSERT | `tenant_id default my_tenant()` | 🔁 **(ปรับตอนทำเฟส 1 · D187)** ตาราง 4 โมดูล **เลิกค่าปริยายของ `entity_id`** (เฟส 2-5 drop default `my_default_entity()`) ⇒ โค้ดต้องส่ง "กิจการที่จอแสดงอยู่" เองทุกครั้ง · ลืมส่ง = not null **ล้มดัง ๆ** · ส่งกิจการเก่าจากแท็บที่ค้างจอ = RLS `with check` ปฏิเสธ · ⚠️ ไม่ใช้ `default my_current_entity()` เพราะแท็บที่ค้างจอกิจการ A จะบันทึกลงกิจการ B (ที่สลับในอีกแท็บ) **เงียบ ๆ** |
| ตอน SELECT/UPDATE/DELETE | RLS `tenant_id = my_tenant()` | RLS `entity_id = (select my_current_entity())` |
| definer (ข้าม RLS) | เช็ค tenant เอง (D46) | เช็คกิจการเอง — ตัวช่วยกลาง `entity_guard()` (ส่วนที่ 4) |

## 2. "กิจการที่เลือกอยู่" — เก็บที่ไหน + `my_current_entity()`

### 2.1 ที่เก็บ (Q8 ✅ ทั้งเบราว์เซอร์กิจการเดียว)
> ✅ **ลงจริงแล้ว (เฟส 1 · migration 0115 · D187)** — ข้อความข้างล่างคือนิยามที่ใช้จริง (ร่างเดิมในส่วนนี้ถูกแทนแล้ว)
- เก็บใน **cookie ของเบราว์เซอร์** `insep_entity` (httpOnly · 1 ปี) — ตั้งโดย `switchEntityAction` (`app/(app)/actions.ts`) **หลัง** `fn_set_last_entity` ยืนยันสิทธิ์ใน DB แล้ว · ออกจากระบบ = ลบ cookie
- `lib/supabase/server.ts` (จุดเดียวที่สร้าง client ของแอป — ไม่มี browser client) แนบ header `x-entity-id` จาก cookie ทุกคำขอ (`entityHeadersFromCookie` ตัดค่าขยะทิ้ง)
  · ไม่ต้องแก้ middleware — header ถูกสร้างฝั่ง server จาก cookie ไม่ได้ส่งต่อจาก request ของเบราว์เซอร์
  · 🔒 header **ไม่ใช่ด่านความปลอดภัย** — ผู้ใช้ยิง PostgREST ตรงด้วย JWT ของตัวเอง + header อะไรก็ได้ ⇒ ด่านจริงคือ `my_current_entity()` ใน DB
- `my_current_entity()` (definer · stable) เลือกชั้นแรกที่ผ่านเงื่อนไข **อยู่ใน tenant + อยู่ในสิทธิ์ (`my_entities()`)**:
  1. header `x-entity-id` → 2. `profiles.last_entity_id` → 3. กิจการหลัก (`is_default`) → 4. กิจการแรกตามรหัส
  · header ปลอม / กิจการของ tenant อื่น / กิจการนอกสิทธิ์ ⇒ **ถูกข้ามไปชั้นถัดไป** (ไม่ error) · ไม่ล็อกอิน / ถูกจำกัดเป็น array ว่าง ⇒ null = ไม่เห็นอะไร
  · 🔁 ต่างจากร่างเดิม ("ไม่มี header = null"): มีชั้นสำรองเพื่อให้ **Claude connector (Q14)** ซึ่งไม่มี cookie ได้กิจการล่าสุดอัตโนมัติ และเปิดแอปครั้งแรกได้กิจการหลัก · ไม่เกิดข้อมูลปนเพราะทุกชั้นคืนกิจการ**เดียว**ที่ผู้ใช้มีสิทธิ์ และการบันทึกต้องส่งกิจการของจอเองอยู่ดี (แถวค่าปริยายข้างบน)
  · SQL Editor / service role ไม่มี `auth.uid()` ⇒ null ⇒ สคริปต์ต้องใส่ `entity_id` เอง (บทเรียน D121)
- 🛡️ **ด่านกันจอค้าง** 2 ชั้น: (ก) insert/update ตรงผ่าน RLS `with check entity_id = my_current_entity()` · (ข) definer เรียก `entity_guard(กิจการของจอ, cap)` → ไม่ตรง = `… (อาจสลับในอีกแท็บ) — รีเฟรชหน้านี้ก่อนบันทึก` (ฝาแฝด TS `ENTITY_MISMATCH_HINT`)
- ตัวสลับบนแถบบน (`app/(app)/_components/EntitySwitcher.tsx`) **ซ่อนจนกว่าจะมีโมดูลทำตาม** — `ENTITY_SCOPED_MODULES` ใน `lib/shared/entityWorkspace.ts` (เฟส 1 = ว่าง) · ตัวสลับที่กดแล้วไม่มีอะไรเปลี่ยน = ปุ่มหลอก · เฟสที่ทำโมดูลเสร็จเติม key ที่นั่นที่เดียว แล้วตัวสลับขึ้นพร้อมบอกบนจอว่า "มีผลกับ: …"
- ป้ายกิจการ **สีประจำกิจการ** บนแถบบนตลอดเวลา + ในการ์ดยืนยันทุกปุ่มบันทึกเงิน/สต็อก (ความเสี่ยงหลักของทาง Y คือ "ลืมว่าอยู่โรงไหน")

### 2.2 ผลต่อ `my_entities()` (D120)
- **ไม่เปลี่ยน** — ยังเป็น "ชุดกิจการที่ผู้ใช้มีสิทธิ์" (null = ทุกกิจการ) · `my_current_entity()` ต้องอยู่ในชุดนี้เสมอ (บังคับในฟังก์ชันข้างบน)
- ตัวสลับบนแถบบนโชว์เฉพาะกิจการใน `my_entities()`
- RLS ฝั่งบัญชีที่ใช้ `my_entities()` อยู่ **คงไว้** (บัญชีดู "ทุกกิจการ" ได้ — Q3 ✅)
- กติกา D120 ทั้งหมดยังอยู่: main จำกัดไม่ได้ · ห้าม array ว่าง · ครบทุกกิจการ = null

## 3. RLS ระดับกิจการ — ตารางที่ต้องเพิ่ม

แพตเทิร์น (ห่อ `(select …)` ตั้งแต่แรก ตามคำแนะนำ Supabase — ของเดิม 221 จุดยังไม่ห่อ):
```sql
using (tenant_id = (select my_tenant()) and entity_id = (select my_current_entity()) and has_cap('…'))
```

| โมดูล | ตารางมี `entity_id` อยู่แล้ว (เปลี่ยน default + RLS) | ตารางลูกที่ **ไม่มี** `entity_id` (ต้องเติม) |
|---|---|---|
| ผลิต | `log_material` `log_ferment` `log_distill` `log_distill_run` `log_ferment_monitor` `log_dilute` `log_product` `log_ferment_draw` `log_redistill` `log_redistill_round` `stock_product` `excise_month_close` + ทะเบียน `materials` `containers` `products` (Q1 ✅ แยก) | — |
| ขาย | `sales_orders` `sale_menu` `warehouse_stock` `stock_moves` `sales_credit_notes` | `sales_order_items` · `sales_payments` · `sales_installments` |
| บาร์ | ทุกตาราง `bar_*` (PK พ่วง entity อยู่แล้ว · ตอนนี้ RLS กรองแค่ tenant) | — |
| เงินเดือน | `employees` `payroll_periods` (ตอนนี้กรอง `my_entities()` → เปลี่ยนเป็นกิจการที่เลือก) | `payroll_items` · `pay_post_legs` · `pay_inputs` `pay_components` `pay_variables` (Q6 ✅ แยก · `pay_rates` ใช้ร่วม ไม่เข้า) |
| ร่วม | `doc_numbering` (มี entity แล้ว) · ❌ `contacts` **ไม่เข้า** (Q2 ✅ ใช้ร่วม) · ❌ `pay_rates` ไม่เข้า | — |

- **ตารางลูก**: เติมคอลัมน์ `entity_id` + FK composite `(tenant_id, entity_id, คีย์แม่)` ชี้ตารางแม่ ⇒ DB การันตีว่าลูกอยู่กิจการเดียวกับแม่ (ดีกว่า RLS แบบ `exists (select … from แม่)` ที่ช้าและหลุดง่าย) · ตารางแม่ต้องมี unique `(tenant_id, entity_id, คีย์)` เพิ่ม
- 🪤 FK composite ที่มี `tenant_id` ห้าม `on delete set null` เปล่า (D137)
- 🪤 policy ถูก OR กัน + `for all` ครอบ SELECT (D85) ⇒ ต้อง drop policy เดิมของทุกตารางแล้วเขียนใหม่ ไม่ใช่เพิ่ม policy
- ⚠️ **ฝั่งบัญชีที่อ่านตารางขาย** (`soi_sel` เปิดให้ `acct.read`) — ถ้าบัญชีดู "ทุกกิจการ" แล้วไปอ่านออเดอร์ จะเห็นแค่กิจการที่เลือกบนแถบบน ⇒ เฟส 3 ต้องไล่ทุกจุดที่บัญชีอ่านตารางขาย/บาร์/เงินเดือน

## 4. definer ที่ข้าม RLS — ต้องเช็คกิจการเองทุกตัว

ตัวช่วยกลางใหม่ `entity_guard(p_entity text, p_cap text) returns uuid` = ยก `bar_guard` (0065) มา + เพิ่มบรรทัด
`p_entity = my_current_entity()` · แล้ว `bar_guard` เรียกตัวนี้ (ไม่เขียนซ้ำ)

**รายชื่อครบ (definer ที่แตะตารางของ 4 โมดูล · นิยามล่าสุด)**

| กลุ่ม | ฟังก์ชัน | ตอนนี้ได้กิจการจาก | ต้องทำ |
|---|---|---|---|

+ insert ตรงจาก `app/(app)/production/actions.ts` ~6 จุด (ได้ค่าปริยายใหม่อัตโนมัติ)

🔧 **เทสอ่านซอร์สบังคับ** (แบบ `entityScope.test.ts` ของ D120): ทุก definer ใน migration ล่าสุดที่แตะตารางในส่วนที่ 3 ต้องเรียก `entity_guard`/`bar_guard` หรืออยู่ในลิสต์ยกเว้นที่มีเหตุผลกำกับ · ทุก policy ของตารางในส่วนที่ 3 ต้องมี `my_current_entity()` · ห้ามเหลือ `my_default_entity()` ในฟังก์ชันของ 4 โมดูล

## 7. บัญชี · คู่ค้า · ผู้ใช้ที่ถูกจำกัด

- **บัญชี** (Q3 ✅): คงตัวเลือกกิจการของบัญชีไว้ (รวม "ทุกกิจการ" สำหรับดู) แต่ **ค่าเริ่มต้น = กิจการบนแถบบน** · บันทึกต้องเป็นกิจการเดียว (Y3/0114 มีแล้ว) · รายงานภาษีต่อกิจการเหมือนเดิม (D124)
- **คู่ค้า** (Q2 ✅ ใช้ร่วม): คงเหมือนวันนี้ทั้ง tenant · ไม่แตะข้อมูล `aim`
- **ผู้ใช้ที่ถูกจำกัด** (D120 · Q11 ✅): บทบาทเดียวทุกกิจการ · สลับได้เฉพาะกิจการในสิทธิ์

## 8. เครื่องมือ "นำเข้าจากอีกกิจการ" (หน้าตั้งค่า · role main เท่านั้น)

> Q13 ✅: นำเข้าได้ **บาร์ทั้งชุด** + **ชุดกติกาเงินเดือน** · ❌ ไม่มีเมนูขาย ❌ ไม่มีทะเบียนผลิต ❌ ไม่มีคู่ค้า (ใช้ร่วมอยู่แล้ว)
> ผู้ใช้ขอให้ทำเป็น **แกนกลาง (know-how)** เพื่อเพิ่มหมวดใหม่ในอนาคตได้ง่าย — ถ้าแต่ละหมวดไม่มีแกนร่วมให้ข้าม
> ⇒ ประเมินแล้ว **มีแกนร่วมจริง** (ทุกหมวดคือ "คัดลอกแถวทะเบียน + จับคู่ด้วยชื่อ + จัดรหัสใหม่ + ตามของที่อ้างถึง") จึงทำเป็นแกน

### 8.1 กติกาที่ทุกหมวดใช้ร่วม (บังคับโดยแกน ไม่ใช่ให้แต่ละหมวดจำเอง)
- **คัดลอกครั้งเดียว** (snapshot) ไม่มีลิงก์ค้าง · role main เท่านั้น · ต้นทาง/ปลายทางอยู่ tenant เดียวกัน · **ปลายทาง = กิจการที่เลือกอยู่เสมอ** (ไม่รับปลายทางจาก client)
- ขั้นตอนบนจอเดียวกันทุกหมวด: เลือกกิจการต้นทาง → ติ๊กหมวด → **พรีวิว** (แต่ละรายการ: ใหม่ / ชื่อซ้ำ = ข้าม / อ้างถึงของที่จะนำเข้าตามไป) → ยืนยัน → รายงาน "นำเข้า N · ข้าม M เพราะ…"
- ชื่อซ้ำในปลายทาง ⇒ **ข้าม ไม่เขียนทับ** (เขียนทับ = แก้ราคา/สูตรของอีกโรงเงียบ ๆ)
- รหัสใหม่ออกด้วยตัวนับของปลายทาง (ไม่ลอกรหัสต้นทาง) · ของที่อ้างกันในหมวดเดียวกันจับคู่ด้วยตาราง "รหัสเดิม → รหัสใหม่" ระหว่างคัดลอก (ถ้าปลายทางมีชื่อนั้นอยู่แล้ว = ชี้ของเดิมในปลายทาง)
- ทั้งหมวดสำเร็จหรือล้มทั้งก้อน (1 transaction) · audit `edit_log` ทำงานตามปกติ (trigger เดิม)
- 🚫 **ห้ามพาไปด้วยเด็ดขาด** — แกนมี "ลิสต์คอลัมน์ต้องห้าม" ที่เทสอ่านซอร์สตรวจ: สต็อก/ยอดคงเหลือทุกชนิด · ราคาทุน/ประวัติราคารับของ · ธุรกรรม/บิล/ออเดอร์/batch/ล็อต/log_* · ใบเอกสาร · งวดเงินเดือน · พนักงาน · ตัวนับเลขเอกสาร

### 8.2 รูปร่างของแกน (สำหรับคนทำเฟส 7)
- **TS** `lib/shared/entityImport.ts`: `IMPORT_KINDS: Record<ImportKind, ImportKindDef>` — ต่อหมวดประกาศ ป้ายบนจอ · ตารางที่คัดลอก (เรียงพ่อก่อนลูก) · คอลัมน์ชื่อที่ใช้ตัดสิน "ซ้ำ" · คอลัมน์ที่คัดลอก (whitelist — ไม่ใช่ "ทุกคอลัมน์ยกเว้น") · ความสัมพันธ์ (คอลัมน์ไหนชี้ตารางไหน) — ใช้ทำพรีวิว + ข้อความบนจอ (D84: ป้ายตาม key ใช้ `Record`)
- **SQL** definer ตัวเดียว `fn_import_from_entity(p_kind text, p_from text, p_ids text[])` → `entity_guard` (main + ปลายทาง = กิจการที่เลือก + ต้นทางอยู่ tenant เดียวกัน) แล้วแตก `case p_kind` ไปบล็อกของแต่ละหมวด (ไม่ใช้ SQL แบบประกอบชื่อคอลัมน์สด — ตรวจไม่ได้ว่าพาคอลัมน์ต้องห้ามไปไหม)
- **เทส**: (1) อ่านซอร์ส — ทุกหมวดใน `IMPORT_KINDS` มีบล็อกใน SQL และกลับกัน · ไม่มีคอลัมน์ต้องห้ามในบล็อกใด (2) `test:tenant` ต่อหมวด 2 ทิศ: นำเข้าแล้วปลายทางได้ครบ + ต้นทางไม่ขยับ + สต็อก/ยอดปลายทางเป็นศูนย์ · นำเข้าซ้ำรอบ 2 = ข้ามทั้งหมด · ผู้ใช้ไม่ใช่ main / ต้นทาง tenant อื่น = ถูกบล็อก
- **วิธีเพิ่มหมวดใหม่ในอนาคต** (เช็กลิสต์ที่ต้องเขียนลง `docs/` ตอนทำเฟส 7): เพิ่ม entry ใน `IMPORT_KINDS` → เพิ่มบล็อก `case` (migration ใหม่ · ยกฟังก์ชันด้วยสคริปต์+diff) → เทสอ่านซอร์สจะแดงจนกว่าจะครบทั้งสองฝั่ง → เพิ่ม `test:tenant` 2 ทิศ

### 9.1 เทส `test:tenant` — พิสูจน์ 2 ทิศ ต่อทุกตารางในส่วนที่ 3
ตั้ง tenant ทดสอบที่มีกิจการ A, B · ผู้ใช้ main 1 คน + ผู้ใช้ถูกจำกัดให้เห็นแค่ A 1 คน แล้วทุกตาราง:
1. **A ไม่เห็นของ B** — เลือก A: select แถวของ B = 0 · update/delete แถวของ B = 0 แถว · insert โดยระบุ `entity_id = B` = ถูกบล็อก
2. **A เห็นของตัวเองครบ** — เลือก A: นับแถวของ A = เท่าที่ seed (กันเทสผ่านเพราะ "ไม่เห็นอะไรเลย")
3. ไม่ส่ง header / header ปลอม / header กิจการ tenant อื่น / ผู้ใช้ถูกจำกัดส่ง B ⇒ เห็น 0 + insert ล้ม
4. definer ทุกตัวในส่วนที่ 4: เรียกด้วยกิจการ/คีย์ของ B ขณะเลือก A ⇒ ถูกบล็อก · เรียกด้วยของ A ⇒ สำเร็จ
5. **ครบวงในกิจการ B**: หมัก → กลั่น → ปรุง → บรรจุ → ขาย/ส่งของ → ภส. ของ B ครบ · ของ A ว่าง · สต็อก B ลด A ไม่ขยับ
6. ข้อมูลเดิม: tenant ที่มีกิจการเดียว ⇒ ตัวเลขทุกจอ/ทุกฟอร์มเหมือนก่อนเฟสเป๊ะ (ถ่ายภาพตัวเลขก่อน/หลัง แบบ D123)

## 11. ข้อมูลเดิม

- ผู้ใช้นับยืนยันแล้ว (2026-11-26) ทั้ง 2 DB: แถวผลิต/ขาย/เงินเดือนทุกแถวอยู่กิจการหลัก ⇒ **ไม่ต้องย้ายข้อมูล** — ตารางลูกที่เติม `entity_id` backfill จากแม่
- ✅ **ผลตรวจก่อนเฟส 1** (`supabase/checks/2026-11-27_entity_workspace_precheck.sql` · ผู้ใช้รัน 2026-11-27):
  - **DB ลูกค้า (proof-app)**: ผ่านครบ 3 ข้อ (ไม่ได้เปิดใช้บาร์)
  - **DB เจ้าของ**: ผลิต/ขาย/เงินเดือน อยู่ EID01 ทุกแถว ✓ · ตัวนำหน้าเลขขายไม่ซ้ำ ✓ · ⚠️ **บาร์ทั้งหมดอยู่ EID02** (ทุกตาราง `bar_*` 100% นอกกิจการหลัก · `bar_entity = EID02`) · `sales_doc_entity` = `sales_revenue_entity` = EID01 ✓
  - ⇒ **ไม่ใช่ข้อมูลปน** — บาร์อยู่กิจการเดียวครบทั้งก้อน (รวมรายการลงบัญชีรายวัน `bar_post` ที่เข้า EID02) ตรงกับทาง Y พอดี: "บาร์ของ EID02 ลิงก์กับบัญชีของ EID02" · **ไม่ต้องย้ายข้อมูล**
  - ผลที่ต้องรู้หลังเฟส 4 (ยุบ `bar_entity`): จะเห็นบาร์ก็ต่อเมื่อเลือก **EID02** บนแถบบน · ถ้าเลือก EID01 บาร์จะว่าง (ถูกต้อง ไม่ใช่ข้อมูลหาย) → ต้องมีป้ายบนจอ "บาร์ของคุณอยู่กิจการ EID02 — สลับไป?" เมื่อกิจการที่เลือกไม่มีข้อมูลบาร์แต่กิจการอื่นมี
  - 🚨 **เฟส 4 ต้องย้ายค่าตั้ง `bar_*` เดิม (ค่ากลางของ tenant) ไปผูก EID02** (= ค่า `bar_entity` เดิม) ไม่ทิ้งไว้เป็นค่ากลาง — ไม่งั้นวันที่ EID01 เปิดบาร์ จะได้พร้อมเพย์/บัญชีรับเงินของ EID02 ไปใช้ = เงินเข้าผิดบริษัท · ทำแบบเดียวกันกับค่าตั้งขาย/เงินเดือนเดิม (ผูกกิจการหลัก)
  - ข้อแนะนำตอนตั้งค่าจริง (เฟส 4 · ใส่ `GOLIVE_CHECKLIST`): บัญชีพนักงานบาร์ที่ไม่ใช่ main ควรจำกัดกิจการให้เห็นแค่ EID02 (D120) ⇒ เข้ามาอยู่ EID02 เลยไม่ต้องสลับเอง
