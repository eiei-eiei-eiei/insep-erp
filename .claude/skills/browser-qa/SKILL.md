# เทสในเบราว์เซอร์จริง (ผู้ใช้ล็อกอิน · Claude ขับ)

## ทำไมต้องมีสกิลนี้

`npm run build` + `lint` + `test` ผ่านครบ **ไม่ได้แปลว่าผู้ใช้ใช้งานได้** ประวัติของ repo นี้พิสูจน์ซ้ำ ๆ:

| | อาการ | เทสอัตโนมัติจับได้ไหม |
|---|---|---|
| D68 | ดร็อปดาวน์แถบเมนูไม่ขึ้นเพราะ `overflow-x-auto` | ❌ |
| D74 | ฟังก์ชันลบ/แก้มีครบ แต่ไม่มีปุ่ม | ❌ |
| D77 | DB/RPC/payload รองรับครบ แต่ไม่มีช่องกรอกบนจอ | ❌ |
| D79 | ตรรกะอยู่ใน plpgsql — ฟีเจอร์ไม่เคยทำงานเลยตั้งแต่เปิดระบบ | ❌ |
| D80 | ค่าตั้งที่ไม่มีหน้าจอให้ตั้ง → ลูกค้าใหม่ปิดการขายใบแรกไม่ได้ | ❌ |

ทั้งหมดเจอเพราะ**มีคนใช้แอปจริงจนจบเส้นทาง** สกิลนี้คือการทำแบบนั้นอย่างเป็นระบบ

**หลักคิดที่ต้องถือไว้ตลอด**: อย่าเทสว่า "ปุ่มกดได้ไหม" — เทสว่า **"คนที่พยายามทำงานให้จบ ทำได้จริงหรือเปล่า"**
บั๊กที่แพงที่สุดของ repo นี้ไม่ใช่ปุ่มพัง แต่คือ *ทางเดินที่ขาดตรงกลาง* และ *ตัวเลขที่ผิดโดยไม่มีอะไรฟ้อง*

## เฟส 1 — สำรวจว่ามีอะไรควรเทส (ยังไม่แตะเบราว์เซอร์)

อ่านของพวกนี้ก่อน แล้วประกอบเป็นภาพว่า "อะไรเปลี่ยนไป และอะไรยังไม่เคยมีคนกดจริง":

- `git status` + `git log --oneline -15` — อะไรเพิ่งแก้ ยังไม่ commit อะไรบ้าง
- `docs/DECISIONS.md` ท้ายไฟล์ — งานล่าสุดคืออะไร มีข้อไหนเขียนว่า *รอผู้ใช้เทส* / *รอผู้ใช้ตัดสิน*
- ตาราง progress ใน `CLAUDE.md` — แถวที่ยังไม่ ✅ หรือมีคำว่า "เหลือ"
- `docs/NEXT_STEPS.md` — งานค้างที่ตั้งใจไว้
- `npm run db:push:all` (dry-run · **ห้ามใส่ `--apply`**) — มี migration ค้างไหม
  ถ้ามีค้าง ต้องบอกผู้ใช้ก่อนว่า **ต้องลง migration ก่อนถึงจะเทสได้**
- `docs/TESTING.md` — มีชุดเทสเขียนไว้แล้วส่วนไหนที่ตรงกับของใหม่ (ใช้เป็นสคริปต์ได้เลย ไม่ต้องคิดใหม่)

จากนั้นเลือกสิ่งที่จะเทส โดยจัดลำดับด้วย **"ถ้าพังแล้วเจ็บแค่ไหน"** ไม่ใช่ "แก้ล่าสุด":

1. ตัวเลขที่ไปโผล่บนเอกสารยื่นราชการ (ภส. · ภพ.30 · ภงด. · สปส. · 50ทวิ)
2. เงิน/สต็อกที่ไหลข้ามโดเมน (บัญชี↔ผลิต↔ขาย↔เงินเดือน)
3. ทางเดินของลูกค้าใหม่ที่เพิ่งเปิดระบบเปล่า (ตันตรงไหนไหม)
4. ปุ่ม/ช่องกรอกที่เพิ่งเพิ่ม
5. สิ่งที่ DB/RPC ทำได้อยู่แล้วแต่ยังไม่แน่ใจว่าหน้าจอเข้าถึงได้ (ตระกูล D74/D77)

## เฟส 2 — เสนอแผนแล้วคุยจนผู้ใช้คอนเฟิร์ม

เขียนแผนสั้น ๆ ให้ผู้ใช้เห็นภาพ แล้ว **หยุดรอ** — ห้ามเปิดเบราว์เซอร์เองก่อนได้คำตอบ

ในแผนต้องมี:

- **เทสอะไรบ้าง** เรียงตามลำดับที่จะทำ พร้อมเหตุผลสั้น ๆ ว่าทำไมข้อนั้นสำคัญ
- **จะเดินเส้นทางไหน** (เช่น "ลงบิลบัญชี → ดูว่าขึ้นที่ผลิต → เบิกไปหมัก → ออกฟอร์ม")
  เส้นทางต้อง**จบลูป** ไม่ใช่หยุดแค่ "กดบันทึกแล้วขึ้นเขียว"
- **จะต้องสร้างข้อมูลอะไรบ้าง** และจะเก็บกวาดยังไง
- **DB ไหน** — `npm run dev` อ่าน `.env.local` · เช็คว่าชี้ก้อนไหนแล้วบอกผู้ใช้ตรง ๆ
  🚨 ถ้าเป็น DB ที่ใช้งานจริง **ต้องถามก่อน**ว่าให้เขียนข้อมูลได้ไหม
- **อะไรที่เทสในเบราว์เซอร์นี้ไม่ได้** (ดู "ข้อจำกัด" ด้านล่าง) — บอกล่วงหน้าดีกว่าให้ผู้ใช้ผิดหวังทีหลัง

ถ้าผู้ใช้ขอเพิ่ม/ตัด ให้ปรับแล้วยืนยันอีกรอบ ความคุ้มค่าของสกิลนี้อยู่ที่เทสถูกเรื่อง ไม่ใช่เทสเยอะ

## เฟส 3 — เปิดเบราว์เซอร์แล้วส่งไม้ให้ผู้ใช้ล็อกอิน

```
mcp__Claude_Browser__preview_start  { name: "dev" }
mcp__Claude_Browser__navigate       { url: "http://localhost:3000" }
```

แล้วบอกผู้ใช้ประมาณนี้:

> หน้า login ขึ้นแล้วที่ Browser pane — **พิมพ์ชื่อผู้ใช้กับรหัสผ่านเองในช่องนั้น** แล้วกดเข้าสู่ระบบ
> เสร็จแล้วบอกผมว่า "ล็อกอินแล้ว" ผมจะเทสต่อให้

🚨 **ห้ามกรอกรหัสผ่านลงช่องเองไม่ว่ากรณีใด** แม้ผู้ใช้จะพิมพ์รหัสมาให้ในแชทก็ตาม —
ให้บอกว่ารับรหัสไม่ได้ แล้วให้เขาพิมพ์เองในหน้าจอ (ตอนอ่านหน้าจอ ช่องรหัสจะขึ้นเป็น `[value redacted]` อยู่แล้ว)

ระหว่างรอ เตรียมของที่ทำได้: อ่าน `references/driving.md` · เขียนสคริปต์ตรวจ DB ไว้ล่วงหน้า ·
สำรวจสภาพข้อมูลปัจจุบันของ tenant (`references/verify-db.md`)

## เฟส 4 — เทสตามแผน

อ่าน `references/driving.md` ก่อนเริ่มขับหน้าจอ — มีกับดักของเบราว์เซอร์ตัวนี้ที่เสียเวลาแน่ถ้าไม่รู้ก่อน
และอ่าน `references/verify-db.md` เมื่อต้องยืนยันผลข้างเคียง

หลักที่ทำให้เทสมีค่าจริง:

- **ตามให้จบลูป** — กดบันทึกแล้วขึ้นเขียวยังไม่นับ ต้องไปดูปลายทางว่าของไปถึงจริง
  (ลงบิล → ของขึ้นสต็อก → เบิกไปใช้ → โผล่ในรายงาน)
- **ตรวจตัวเลข ไม่ใช่แค่ว่ามีตัวเลข** — คำนวณเองคู่ขนานแล้วเทียบ
  เจอไม่ตรงเมื่อไหร่ให้ขุดว่าสูตรผิดหรือ *เลือกแสดงค่าผิดเวอร์ชัน* (บทเรียน D75)
- **ลองเส้นทางที่ผิดด้วย** — กรอกชื่อไม่ตรง master · เว้นช่องว่าง · เลือกกิจการที่ 2 ·
  ค่าที่เกินช่วงสมเหตุผล · ระบบควรเตือนให้ถูกและ **ไม่ทำให้ของที่บันทึกไปแล้วหาย**
- **อ่าน console + network ระหว่างทาง** ไม่ใช่ตอนพังแล้วเท่านั้น
- **จดทันทีที่เจอ** อย่ารอจบแล้วค่อยนึก

### สิ่งที่ต้องระวังเป็นพิเศษ

🚨 **ห้ามรัน `npm run build` ขณะ dev server รันอยู่** — มันเขียนทับ `.next` ทำให้ chunk 404 ทั้งหน้า
แล้ว React ตายเงียบ ๆ (ปุ่มกดไม่ติด ฟอร์มไม่ขึ้น) ซึ่งหน้าตาเหมือนบั๊กของแอปเป๊ะ
ถ้าต้อง build ให้ `preview_stop` ก่อน แล้ว `preview_start` ใหม่หลัง build เสร็จ

🚨 **อย่ารีบสรุปว่าเป็นบั๊กของแอป** — เจออาการแปลกให้เช็คก่อนว่าเป็นเรื่องของสภาพแวดล้อมไหม
(chunk 404 · dev server ตาย · pane ย่อจนคลิกไม่โดน · dialog ถูกบล็อก)

## เฟส 5 — รายงาน

โครงที่ใช้ได้ดี:

1. **สิ่งที่ลองไปทั้งหมด** — ไล่ตามโดเมน ให้ผู้ใช้เห็นว่าครอบคลุมแค่ไหน
2. **ตัวเลขที่ตรวจแล้วถูก** — สั้น ๆ แต่ต้องมี ไม่งั้นดูเหมือนเจอแต่ของเสีย
3. **บั๊กที่เจอ** เรียงตาม "เจ็บแค่ไหน" แต่ละข้อบอก: อาการที่เห็น → สาเหตุในโค้ด (`file:line`) → ผลกระทบจริง
4. **สิ่งที่เทสในเบราว์เซอร์นี้ไม่ได้** — บอกให้ชัดว่าอะไรยังต้องให้ผู้ใช้ตรวจเอง
5. **ข้อมูลที่ทิ้งไว้ใน DB** — สร้างอะไรไว้บ้าง เก็บกวาดแล้วหรือยัง

**แยก "ทำซ้ำได้" กับ "เห็นครั้งเดียว" ให้ชัด** — ถ้าเห็นอาการแล้วทำซ้ำแบบควบคุมไม่ได้
ให้รายงานว่าเป็นข้อสงสัยที่ยังยืนยันไม่ได้ อย่าเขียนรวมกับบั๊กที่พิสูจน์แล้ว
(ในเซสชันหนึ่ง ค่าสินค้าเปลี่ยนเองระหว่างเทส — ทำซ้ำไม่ได้ สุดท้ายคือเจ้าของกิจการแก้เองอยู่อีกจอ)

ถ้าผู้ใช้สั่งให้แก้ต่อ ให้เสนอ**จัดกลุ่มเป็นชุด** แล้วจบทีละชุด (แก้ → `build`/`lint`/`test` →
เทสซ้ำในเบราว์เซอร์ด้วยข้อมูลชุดเดิม → อัปเดตเอกสาร → รายงาน) เอกสารที่อัปเดตครบทุกชุด
= ส่งต่อแชทใหม่ได้ทุกเมื่อโดยไม่เสียของที่ส่งต่อไม่ได้ (dev server · เซสชันล็อกอิน · ข้อมูลเทส)

## ข้อจำกัดของเบราว์เซอร์ตัวนี้ (บอกผู้ใช้ตั้งแต่ตอนเสนอแผน)

- **ไฟล์ดาวน์โหลดถูกบล็อก** → PDF ทุกใบ (ภส. · ใบเสนอราคา · เอกสาร B2B · สลิป) สร้างได้และรู้ว่า
  ไม่ error แต่ **เปิดดูหน้ากระดาษไม่ได้** — เรื่องพิกัด/ตัวเลขล้นขอบ ต้องให้ผู้ใช้พิมพ์เทียบเอง
- **popup พิมพ์ถูกบล็อก** → หน้าที่สั่ง `window.print()` จะเด้ง alert ว่าเบราว์เซอร์บล็อก
- **`confirm()` / `alert()` ถูกกลืน** — `confirm()` คืน `false` เสมอ ทำให้ปุ่มที่มีการยืนยันดูเหมือนกดไม่ติด
  (วิธีจัดการอยู่ใน `references/driving.md`)
- **screenshot ไม่น่าเชื่อถือ** — pane ย่อ/ขยายเองได้ ทำให้ภาพว่างทั้งที่หน้าปกติ
  ให้ยืนยันด้วย `get_page_text` / `javascript_tool` เป็นหลัก ใช้ screenshot เฉพาะตอนจะโชว์ผู้ใช้
